# 이 프로젝트를 어떻게 세팅했나

이불공장 납품·정산 관리 사이트를 만들기 전에, 먼저 **일하는 판을 깔았다.**
요구사항 문서 한 장에서 시작해 작업 목록, 그 목록을 다루는 도구, 지켜야 할
규칙, 그 규칙을 강제하는 장치, 일을 나눠 맡을 조수까지 만들었다.

코드는 아직 한 줄도 안 썼다. 그런데 왜 이런 걸 먼저 만들었을까.

---

## 왜 판부터 깔았나

요구사항 문서를 AI에게 통째로 주고 "이대로 만들어줘"라고 하면 어떻게 될까.
처음 한두 시간은 잘 돌아간다. 문제는 그다음이다.

**어디까지 했는지 모른다.** 대화가 길어지면 앞부분이 잘려 나간다. 어제 만든
걸 오늘 또 만들고, 만들었다고 생각한 게 실은 없다.

**규칙을 잊는다.** "부가세는 전체를 합산한 뒤 한 번만 계산한다"고 열 번째
줄에 적혀 있어도, 200번째 줄쯤 가면 잊는다. 이걸 잊으면 정산 금액이
틀어지고 원청과 돈 문제가 생긴다.

**파일이 걷잡을 수 없이 커진다.** 한 파일에 계속 붙이다 보면 800줄짜리
컴포넌트가 나오는데 그때 가서 나누려면 처음부터 다시 쓰는 것과 비슷한 일이
된다.

**검증을 건너뛴다.** "다 만들었습니다"라고 보고했는데 빌드가 안 되는 경우가
생긴다. 확인을 안 해서는 아니다. 확인하는 단계가 흐름에 없다.

이 네 가지는 AI가 게을러서 생기지 않는다. **기억에 의존하는 구조라서**
생긴다. 그래서 일을 기억에서 떼어내 **파일과 장치**에 맡기기로 했다.

> 공장으로 비유하면 이렇다. 숙련공 한 명에게 "알아서 잘 만들어 주세요"라고
> 맡기지 않고 작업 지시서를 쓰고 공정표를 붙이고 불량품이 다음 공정으로
> 못 넘어가게 검사대를 세웠다. 사람이 덜 똑똑해서가 아니다. 그래야 어제와
> 오늘이 같은 품질로 나온다.

## 1단계 — 요구사항을 작업으로 쪼갰다

### 무엇을 했나

`설계.md`는 26개 절로 된 요구사항 문서다. 원청 관리, 품목 관리, 송장 작성,
월별 단가, 월말 정산, 이메일 발송까지 만들 것이 전부 적혀 있다. 이걸
**30분짜리 작업 96개**로 쪼갰다.

쪼갠 결과는 `backlog.json` 한 파일에 담았고, 작업마다 상세 문서를 하나씩
만들어 `docs/tasks/T-001.md`부터 `T-096.md`까지 96개를 붙였다.

### 왜 30분인가

작업 단위가 너무 크면 "송장 기능 만들기" 같은 게 되는데 이건 시작도 끝도
흐릿해서 절반쯤 하다 멈추기 쉽다. 반대로 너무 작으면 관리하는 품이 일하는
품보다 커진다.

30분은 한 번에 끝까지 갈 수 있는 크기다. 시작할 때 끝이 보이고, 끝났을 때
"됐다"고 말할 수 있다. 96개를 다 더하면 48시간이다.

### 작업마다 무엇이 붙어 있나

| 항목 | 예시 |
| --- | --- |
| id | `T-044` |
| 제목 | 송장 확정과 번호 부여 |
| 설명 | 확정 시점에 이어지는 일련번호를 부여하고 상태를 바꾼다 |
| 상세 문서 | `docs/tasks/T-044.md` |
| 상태 | 할 일 / 작업중 / 리뷰필요 / 사람 판단 필요 / 대기 / 완료 / 취소 |
| 우선순위 | P0~P3 |
| 선행 작업 | T-009, T-043이 끝나야 시작 가능 |
| 요구사항 근거 | 설계.md §7 |

96개를 순서 없이 늘어놓으면 뭘 먼저 해야 할지 알 수 없다. **선행 작업** 칸에
"이 작업은 저 작업이 끝나야 시작할 수 있다"를 적어 두면, 지금 당장 손댈 수
있는 작업만 골라낼 수 있다.

**요구사항 근거**도 마찬가지다. 각 작업이 요구사항 문서의 몇 번째 절에서
나왔는지 적어 두면, 나중에 "이거 왜 이렇게 만들기로 했지?" 싶을 때 원문으로
바로 돌아갈 수 있다.

### 상태를 7가지로 나눈 이유

흔히 쓰는 건 세 가지다. 할 일, 하는 중, 끝남. 실제로 일하다 보면 이 셋으로
안 담기는 상황이 생긴다.

- **사람 판단 필요** — 사장님이 실제 공장 주소를 알려줘야 진행되는 작업이
  있다. 이건 AI가 아무리 노력해도 못 푼다.
- **대기** — 앞 작업이 안 끝나서 못 하는 것. 위와는 성격이 다르다.
- **리뷰필요** — 만들긴 했는데 확인이 남은 것.
- **취소** — 안 만들기로 한 것. 지우지 않고 남겨야 나중에 "왜 없지?" 할 때
  답이 나온다.

이 중 **대기·사람 판단 필요·취소**는 반드시 사유를 적게 했다. 사유 없이 멈춰
있는 작업은 시간이 지나면 아무도 못 푼다.

### 지금 막혀 있는 것

96개 중 2개가 시작부터 막혀 있다. 둘 다 사람이 풀어야 한다.

- **T-001** — 공장 정보 실제 값, 사이트 전용 이메일 주소, 배포 도메인
- **T-096** — 지금 쓰고 있는 정산 엑셀 양식 파일

요구사항에 "기존 엑셀 양식의 필수 내용을 유지한다"고 적혀 있으니 원본을
보지 않고는 만들 수 없다. 이런 건 숨기지 말고 처음부터 드러내 두는 게 낫다.

## 2단계 — 백로그를 다루는 도구를 만들었다

### 왜 JSON을 직접 고치면 안 되나

`backlog.json`은 3천 줄이 넘는다. 이걸 그냥 열어서 읽으면 대화창이 작업 목록
하나로 꽉 찬다. 정작 일할 공간이 없어진다.

손으로 고치는 것도 문제다. 상태 값을 오타로 적거나, 없는 작업을 선행 작업으로
걸거나, 완료로 바꾸면서 완료일을 안 넣으면 파일이 조용히 망가진다. 망가진 걸
나중에 알아차리면 어디서부터 틀렸는지 찾기 어렵다.

**전용 도구**를 만들었다. `tools/backlog.mjs`, 660줄짜리 명령줄 프로그램이다.

### 무엇을 할 수 있나

```bash
node tools/backlog.mjs              # 안 끝난 작업 전부
node tools/backlog.mjs next         # 지금 당장 시작할 수 있는 작업
node tools/backlog.mjs get 44       # 한 작업 자세히 보기
node tools/backlog.mjs stats        # 단계별 진행률

node tools/backlog.mjs set 44 진행   # 상태 바꾸기
node tools/backlog.mjs edit 44 --priority P0
node tools/backlog.mjs add --title "인쇄 여백 보정" --category ui --phase "2. 송장"
```

`next`가 이 도구의 핵심이다. 96개 중에서 선행 작업이 전부 끝난 것만 골라
보여준다. "지금 뭐 하지"에 대한 답이 한 줄로 나온다.

### 사람이 치기 편하게

명령을 외우기 어려우면 안 쓰게 되니까 여러 방식으로 받아 준다.

```bash
node tools/backlog.mjs 44           # 번호만 쳐도 상세가 나온다
node tools/backlog.mjs set 2 진행    # in_progress / 작업중 / 진행 다 된다
node tools/backlog.mjs get "예외 단가"  # 제목 일부로도 찾는다
node tools/backlog.mjs list --phase 송장  # "2. 송장"을 다 안 써도 된다
```

### 파일을 지키는 두 가지 장치

**저장 전에 전부 검사한다.** 상태를 하나 바꿔도 96개 전체를 훑어서 중복된
번호, 잘못된 상태 값, 없는 선행 작업, 순환 참조, 빠진 문서를 본다. 하나라도
걸리면 파일을 아예 건드리지 않는다.

실제로 시험해 봤다. 두 작업이 서로를 선행 작업으로 걸도록 명령을 넣었더니
"선행 작업 순환: T-036 → T-037 → T-036"이라며 거부했고, 파일은 그대로였다.

**임시 파일에 쓰고 바꿔치기한다.** 원본에 바로 쓰다가 중간에 끊기면 파일이
반쪽이 된다. 임시 파일에 다 쓴 다음 이름만 바꾸면, 끊기더라도 원본은 멀쩡하다.

## 3단계 — 규칙을 문서로 적었다

### 무엇을 적었나

`CLAUDE.md`를 만들었다. 매번 작업을 시작할 때 자동으로 읽히는 파일이다.
여기에는 항상 필요한 것만 짧게 담았다.

- 이 프로젝트가 무엇인지, 쓰는 사람이 누구인지
- 골든 룰 6개
- 작업 흐름 6단계
- 규칙 문서 목차

그리고 깊은 내용은 `.claude/rules/` 아래 5개 문서로 나눴다. 필요할 때만 읽으면
되는 것들이다.

| 문서 | 내용 |
| --- | --- |
| 도메인-불변식.md | 틀리면 돈이 어긋나는 규칙 |
| 백로그-운영.md | 작업 상태를 어떻게 다루나 |
| 코드-작성.md | 파일 크기, 화면 제약, 검증 |
| git-과-하네스.md | 브랜치, 커밋, 장치 동작 |
| 서브에이전트.md | 조수를 언제 부르나 |

### 가장 중요한 문서

`도메인-불변식.md`에는 요구사항 문서 26개 절에서 "비슷하게 만들면 안 되는
것"만 뽑아 담았다.

몇 가지 예를 보자.

**부가세 계산.** 요구사항에는 "부가세는 전체 공급가액을 합산한 뒤 한 번
계산하고 원 단위에서 반올림한다"고 적혀 있다. 줄마다 부가세를 계산해서
더하는 것과 결과가 다른데, 100줄짜리 정산서라면 수백 원이 어긋나고 원청이
검산하면 바로 드러난다.

**송장번호.** 두 사람이 사무실과 작업장에서 동시에 송장을 확정하는 일이
실제로 생긴다. 프로그램이 "지금까지 제일 큰 번호 + 1"로 번호를 만들면, 두
사람이 동시에 누를 때 같은 번호가 두 장에 찍힌다. 그러면 월말에 어느 것이
진짜인지 가릴 수 없다. 그래서 번호는 데이터베이스가 직접 발급하게 해야 한다.

**품목 이름.** 원청이 품목 이름을 바꾸면 곤란한 상황이 생긴다. 이미 출력해서
도장 찍은 종이 송장에는 옛 이름이 적혀 있는데, 사이트에서 이름을 바꿔 버리면
종이와 화면이 달라진다. 이름은 세 곳에서 다르게 보여야 한다.

| 어디 | 무엇을 보여주나 |
| --- | --- |
| 과거 송장 | 그 송장을 쓸 당시의 이름 (영원히 안 바뀜) |
| 사이트 검색 | 새 이름으로 찾아도 옛 이름 송장이 함께 나옴 |
| 정산서 엑셀 | 최종 이름만. 옛 이름은 원청에게 안 보냄 |

**직원에게 금액 감추기.** 직원은 단가와 정산 금액을 보면 안 된다. 그런데
화면에서 가리는 것만으로는 부족하다. 데이터는 이미 컴퓨터까지 왔고,
브라우저 개발자 도구를 열면 그대로 보인다. **서버가 보낼 때부터 빼야** 한다.

각 항목에는 요구사항 문서의 절 번호를 붙였다. 판단이 안 서면 원문으로
돌아가면 된다.

## 4단계 — 규칙을 장치로 강제했다

### 문서만으로는 안 지켜진다

규칙을 아무리 잘 써 놔도 대화가 길어지면 흐려진다. 그래서 **어길 수 없게**
만들기로 했다. Claude Code의 **hook**이라는 기능을 썼다.

hook은 쉽게 말하면 **자동 검사대**다. 파일을 저장하기 직전, 명령을 실행하기
직전 같은 정해진 순간에 미리 정해 둔 프로그램이 끼어들어 검사한다. 통과하면
그냥 지나가고, 문제가 있으면 막는다.

공장 검사대와 같다. 작업자에게 "불량품 내보내지 마세요"라고 말로 부탁하는
것과, 불량품이 통과 못 하는 장치를 라인에 세우는 것은 다르다.

### 7개를 만들었다

**① 세션을 열면 브랜치를 알려준다**

작업을 시작할 때 지금 어느 브랜치에 있는지 띄운다. `main`이면 "작업 전에
`dev`로 옮기라"고 안내한다. `dev`가 있으면 `git switch dev`, 없으면
`git switch -c dev`라고 실제로 쳐야 할 명령까지 알려준다.

옮기지는 않는다. 작업하던 게 남아 있을 수 있으니 판단은 사람이 한다.

**② 작업 목록 파일을 못 열게 막는다**

`backlog.json`을 직접 읽거나 고치려 하면 막고, 대신 써야 할 명령을 보여준다.
`cat`이나 `jq` 같은 셸 명령으로 우회하는 것도 막는다. 도구를 통한 접근과
`git` 명령은 통과시킨다.

**③ 작업을 안 잡았으면 파일을 못 고치게 막는다**

"작업을 시작하면 상태를 작업중으로 바꾼다"는 규칙이 있는데, 이것도 장치로
만들었다. 작업중인 작업이 하나도 없으면 코드 파일 수정이 막힌다.

막을 때 그냥 막지 않고 길을 알려준다.

```
1) 백로그에 있는 작업이면 → next로 찾아서 set <id> 진행
2) 백로그에 없는 즉흥 작업이면 → add로 등록부터
3) 백로그와 무관한 일이면 → 사용자에게 확인
```

즉흥 작업이 생기면 막지 않고 **기록하게** 만든다. 2번이 그 자리다.

**④ 파일이 길어지면 경고하고, 넘으면 되돌린다**

파일 성격마다 줄 수 한도를 다르게 뒀다.

| 어떤 파일 | 한도 | 경고 |
| --- | --- | --- |
| 화면 컴포넌트 | 200줄 | 170줄 |
| API 라우트 | 150줄 | 128줄 |
| 도메인 로직 | 250줄 | 213줄 |
| 테스트 | 400줄 | 340줄 |
| 데이터베이스 마이그레이션 | 제한 없음 | |

85%를 넘으면 "한도에 가깝다. 남은 여유는 36줄이다"라고 알려준다. 이때 나누는
게 싸다. 다 쓰고 나서 800줄을 쪼개는 것보다 훨씬.

한도를 넘기면 되돌려서 다시 하라고 한다. 이때 "한도가 잘못됐다고 판단되면
임의로 넘기지 말고 사용자에게 조정을 요청하라"는 문구를 같이 넣어 스스로
규칙을 풀어 버리지 못하게 했다.

**⑤ 파일을 고칠 때마다 문법 검사, 턴이 끝날 때 빌드**

파일 하나를 고치면 그 파일만 검사한다. 빠르니까 매번 할 수 있다.
전체 빌드는 느리니까 대화가 끝날 때 한 번만 돌린다. 실패하면 대화를 못 끝낸다.

한 가지 구멍을 미리 막아 뒀다. 검사받기 전에 커밋해 버리면 "바뀐 게 없으니
검사 안 해도 되겠네"가 될 수 있어서 이번 대화에서 커밋된 것까지 검사 대상에
넣었다.

**⑥ 작업 목록이 바뀌면 자동으로 커밋한다**

상태를 바꾸면 알아서 커밋된다. 커밋하는 걸 신경 쓸 필요가 없다.

**⑦ 작업이 끝나면 전부 커밋하고 올린다**

어떤 작업을 완료로 바꾸면, 그 작업으로 만든 코드까지 전부 묶어서 커밋하고
원격 저장소로 올린다. 커밋 메시지에는 무엇이 끝났는지와 진행률이 들어간다.

```
feat(backlog): T-002 Next.js 프로젝트 초기화 완료

완료 작업:
- T-002 Next.js 프로젝트 초기화

진행: 1/96
```

완료 여부는 도구 호출을 감시하지 않고 직전 커밋과 지금 파일의 완료 목록을
비교해서 판단한다. 어떤 경로로 바뀌었든 잡히고, 같은 작업을 두 번 올리지
않는다.

### 진짜 도는지 확인했다

만들어 놓고 "되겠지" 하면 안 된다. 실제로 시험했다.

가짜 원격 저장소를 하나 만들고, 프로젝트 사본을 거기에 연결한 다음
`set 2 done`을 실행했다. 코드 파일 하나와 작업 목록이 한 커밋으로 묶여
원격까지 올라갔고, 같은 명령을 한 번 더 돌렸더니 중복 커밋이 생기지 않았다.

줄 수 검사는 260줄짜리 임시 파일을 만들어 확인했다. 한도 250줄을 넘겼다고
막았고, 663줄짜리 실제 파일에는 "95%"라고 경고가 떴다.

## 5단계 — 일을 나눠 맡겼다

### 조수 둘을 뒀다

일을 혼자 다 떠안지 않고 성격이 다른 일은 떼어 다른 조수에게 맡기기로 했다.
**서브에이전트**라고 부른다.

**정찰병 (task-briefer)** — 작업을 시작하기 전에 부른다. 작업 정보를 읽고,
요구사항 원문을 찾아보고, 저장소를 뒤져 관련 파일을 모은다. 그리고 두 가지를
작업 문서에 적어 둔다.

- **쉬운 설명** — 이 작업이 공장에서 무슨 문제를 푸는지 3~5문장
- **관련 파일** — 이미 있는 파일과 앞으로 만들 파일을 나눠서

빠르고 싼 모델(Haiku)을 붙였다. 찾아서 적는 일이라 무거운 모델이 필요 없다.

**검사관 (adversarial-reviewer)** — 작업이 끝난 뒤 부른다. 이 조수의 일은
칭찬이 아니라 **깨뜨리기**다. 부가세를 줄마다 계산하지 않았는지, 송장번호를
프로그램에서 만들지 않았는지, 직원에게 금액이 새는 경로가 없는지 찾는다.

깊이 봐야 하는 일이라 무거운 모델(Opus)을 붙였다.

### 검사관에게는 고칠 권한을 주지 않았다

일부러 그랬다. 검사관이 직접 고쳐 버리면 그 수정을 누가 검사하는지가
사라진다. 지적만 하고 고치는 건 원래 하던 쪽이 한다.

그리고 지적할 때 "에러 처리가 부족해 보인다" 같은 막연한 말을 못 하게 했다.
반드시 어떤 값을 넣으면 무슨 일이 벌어지는지를 붙이게 했다.

> "단가가 미정인 줄이 섞이면 41행에서 그대로 곱해 계산이 깨진다"

이래야 지적을 받은 쪽이 확인할 수 있다.

마지막에 **"확인 못 한 영역"**도 반드시 적게 했다. 무엇을 안 봤는지 모르면
그 검사 결과를 믿을 수 없다.

## 세팅하면서 배운 것

### 규칙과 장치는 쌍이다

문서에만 있고 장치가 없으면 안 지켜진다. 장치만 있고 문서가 없으면 왜 막히는지
몰라서 우회할 궁리를 한다. 둘을 같이 만들어야 한다.

막을 때마다 이유와 해결 방법을 같이 보여주게 했다. 막혔을 때 고장을 의심하지
않고 규칙이라는 걸 바로 안다.

### 가드는 과잉일 수 있다

만들면서 실제로 겪은 일이다.

작업 목록 파일을 지키는 장치를 만들었는데 이게 파일 이름이 글자로
들어가기만 해도 막았다. 그 파일을 설명하는 규칙 문서를 쓰려는데 자꾸
차단됐다. 문서에 파일 이름을 적는 것뿐인데 말이다.

우회할 방법은 있었다. 하지만 스스로 만든 규칙을 스스로 피해 가는 건 앞뒤가
안 맞는다. 그래서 장치를 고쳤다. 명령문 안의 **긴 글 덩어리는 명령이 아니라
데이터**로 보고 검사에서 빼도록 했다.

고친 뒤 다시 확인했다. 실제로 파일을 읽거나 고치려는 시도 다섯 가지는
그대로 막히고, 문서에 이름을 적는 건 통과한다.

**교훈** — 막는 장치는 세게 만들기 쉽다. 그런데 정당한 일까지 막으면 결국
꺼 버리게 된다. 실제로 써 보면서 조여야 한다.

### 만들고 나서 반드시 돌려 봐야 한다

조수 둘을 만들고 실제로 불러 봤더니 두 가지가 나왔다.

**이번 대화에서는 못 쓴다.** 조수 정의는 대화를 시작할 때만 읽힌다.
Claude Code를 다시 켜야 쓸 수 있다.

**설정 파일에 문법 오류가 있었다.** 설명 글에 `(예: T-044)`라고 썼는데,
이 설정 파일 형식에서는 콜론 뒤에 띄어쓰기가 오면 구분자로 해석된다.
그대로 뒀으면 다음에 켰을 때 조용히 로드되지 않았다. 오류 메시지도 없이
그냥 없는 조수가 됐다.

실제로 불러 보지 않았으면 못 찾았다.
