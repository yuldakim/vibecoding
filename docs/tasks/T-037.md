## 목적

수량은 오입력이 곧 오납품·오정산이 된다. 큰 숫자 입력과 즉각적인 합계 표시로 실수를 줄인다.

## 작업 범위

- 줄별 사이즈 선택(기본 4종 + 직접 입력)
- 수량 입력(숫자 키패드 친화, 0·음수 차단)
- 전체 납품 수량 실시간 합계 표시
- 품목마다 사이즈를 제한하지 않음

## 완료 기준

- [x] 수량 0이나 음수가 저장되지 않는다 — 클라이언트(저장 버튼 클릭 시 `Number.isInteger && > 0` 검증, 실패하면 이동 자체를 안 함)와 서버(`line-editor.tsx`의 `parseLine`이 `quantity <= 0`이면 그 줄 자체를 버림) 이중 방어. 브라우저로 수량 0 저장 시도 → 거부 메시지 확인, URL을 직접 조작해 `line=255:1:-3`을 끼워넣어도 그 줄만 조용히 걸러지고 나머지는 정상 표시되는 것 확인
- [x] 전체 수량 합계가 줄 변경 즉시 갱신된다 — 사이즈·수량 편집은 클라이언트 컴포넌트(`LineRowEditor`)가 새 상태로 URL을 다시 계산해 이동하고, 그 즉시 서버 컴포넌트가 전체 줄을 다시 합산해 "N줄 · 전체 M장"으로 보여준다. 브라우저로 수량 1→5 저장 후 "전체 5장"으로 바뀌는 것 확인
- [x] 모든 품목에서 모든 사이즈를 고를 수 있다 — 품목별 사이즈 제한 로직이 어디에도 없다. `SizeSelect`(T-034, `components/size-select/`)를 그대로 재사용해 기본 4종 + 직접 입력을 그대로 가져옴(직접 입력한 사이즈는 `sizes` 테이블에 저장돼 다음 송장부터도 선택 가능 — T-034가 이미 만든 동작)

검증: `npx tsc --noEmit`·`npm run lint`·`npm run build` 통과. 브라우저로 품목 추가(기본 싱글·1장) → 사이즈를 퀸으로, 수량을 5로 변경·저장 → 합계 갱신 확인.

**adversarial-reviewer가 치명으로 지적해 고친 것**: 최초 구현은 줄이 2개 이상일 때만 드러나는 버그가 있었다 — "저장"이 편집한 줄을 목록 맨 뒤로 보내면서 `key={i}`(배열 인덱스)를 쓰고 있어서, 순서가 바뀌면 React가 같은 위치의 컴포넌트를 재사용해 **다른 줄의 입력 상태가 엉뚱한 줄에 붙었다**(품목A를 9장으로 고치면 화면엔 품목B가 9장으로 보이고, 그 상태에서 다시 저장하면 실제로 품목B가 9장으로 잘못 기록됨). `line=` 인코딩에 `lineKey`(줄이 생성될 때 한 번 정해지는 고유 식별자)를 추가해 `key={line.lineKey}`로 바꾸고, 저장 시 원래 위치에 그대로 끼워 넣도록(`splice`) 고쳤다. 실제 브라우저로 2줄·3줄(가운데 삭제 포함) 시나리오 모두 재현 후 값이 안 섞이는 것 확인.

**같은 뿌리의 문제가 재확인 리뷰에서 3건 더 나와서 마저 고쳤다** (중요 등급): ① `line-row-editor.tsx`가 `line-codec.ts`의 `encodeLine`을 안 쓰고 직접 문자열을 조립하고 있어서, 다음 작업(T-038)이 인코딩에 필드를 추가하면 이 파일만 안 고쳐져 저장한 줄이 조용히 사라질 뻔했다 — `encodeLine`/`MAX_QUANTITY`를 import해서 쓰도록 고침. ② `lineKey`(줄 식별자)를 정수인지만 보고 값 자체(0 이하·안전 정수 범위 밖)나 중복은 검증 안 해서, URL을 조작해 두 줄에 같은 lineKey를 주면 이번에 고친 치명 버그가 그대로 재현될 수 있었다 — `parseLine`에 `lineKey > 0`·안전 정수 검증을 추가하고, `line-editor.tsx`에서 중복 lineKey는 먼저 나온 것만 남기도록 고침. ③ `key={line.lineKey}`만 쓰면 **이 줄 자신의** 사이즈·수량이 서버에서 바뀌어도(예: 저장 후 브라우저 뒤로가기) 컴포넌트가 재사용돼 입력칸에 옛 값이 남을 수 있었다 — `key`를 `${lineKey}:${sizeId}:${quantity}` 복합값으로 바꿔 이 줄 자신의 값이 실제로 바뀌면 항상 리마운트되게 함. 브라우저로 "저장 후 뒤로가기" 시나리오 재현: 수량 9로 저장 → URL이 9로 바뀜 확인 → 뒤로가기 → URL이 1로 돌아가고 화면도 정확히 1로 돌아오는 것 확인(수정 전이었다면 입력칸에 9가 그대로 남았을 상황).

`app/invoices/new/line-codec.check.ts`(신규, `npm run check:invoice-line-codec`)로 인코딩 왕복·경계값(수량 0·음수·상한 초과, lineKey 0·음수·범위초과, 필드 개수 오류)과 줄 순서 복원(splice 재삽입) 로직을 자동 검증하도록 추가함 — 이번 치명 버그가 정확히 이 부분이었어서, 다음에 같은 실수가 나면 브라우저 없이도 바로 잡힌다.

그 외 adversarial-reviewer 지적으로 함께 고친 것:
- `sizeId`는 검증 안 하고 있었다 — `line=254:9999:5:1`처럼 존재하지 않는 사이즈 id를 끼워넣어도 유효한 줄로 살아남았다. `sizes` 목록과 대조해 없는 sizeId는 버리도록 고침(브라우저로 확인)
- 줄 품목 조회가 실패하면 지금까지 담아온 줄을 전부 비웠다(`lineItemsError ? [] : ...`) — 일시적 DB 오류 한 번에 최대 20줄이 날아갈 수 있었다. T-036의 원래 패턴(조회 실패 시 최대한 보존)으로 되돌림
- `getSizes()`가 예외를 던지는데 아무도 안 잡아서, 사이즈 조회가 한 번 실패하면 `/invoices/new` 페이지 전체가 Next 기본 에러 화면으로 죽었다. try/catch로 감싸 에러 문구로 대체
- 수량 입력을 공통 `Input` 컴포넌트 대신 손으로 만들어서 `label`과 `input`이 `htmlFor`/`id`로 연결 안 돼 있었다(휴대폰에서 "수량(장)" 글자를 눌러도 포커스 안 감) — `Input` 재사용으로 교체
- 수량 상한이 없어 `9999999...` 같은 값도 통과했다 — 1~9999 범위로 제한
- T-036이 "다음 입력(사이즈·수량)으로의 포커스 이동은 T-037에서 다시 판단한다"고 남긴 약속에 대한 결정: **자동 포커스를 넣지 않기로 했다.** 이유는 T-036과 같다 — 추가·삭제·저장이 전부 풀 페이지 네비게이션이라 자동 포커스를 넣으면 다른 줄을 삭제만 해도 포커스가 튀어 휴대폰에서 소프트 키보드가 열린다.
