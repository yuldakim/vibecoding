# T-007 · 마이그레이션: 품목·품목 이력

> 작업 상태의 SSOT는 저장소 루트의 `backlog.json`이다. 이 문서는 무엇을 왜 어떻게 만드는지만 다룬다.

| 항목 | 값 |
| --- | --- |
| 단계 | 0. 기반 구축 |
| 분류 | 데이터 모델 |
| 우선순위 | P0 |
| 예상 시간 | 30분 |
| 선행 작업 | [T-004](T-004.md) 전체 DB 스키마 설계 확정 |
| 요구사항 근거 | §4 품목 관리, §4 품목명 변경 규칙 |
| 주요 위치 | `supabase/migrations/` |

## 목적

품목은 이름이 바뀌고 서로 합쳐지는데도 과거 송장의 이름은 보존돼야 한다. 현재 이름 테이블과 별칭(이전 이름) 테이블을 분리해 검색과 표시를 동시에 만족시킨다.

## 요구사항 근거 (설계.md 인용)

> 품목은 원청별로 따로 관리한다. 한 원청에 50~100개 이상의 품목이 등록될 수 있다.
>
> 사이트 검색에서는 새 이름으로 검색해도 이전 이름으로 작성된 송장이 함께 조회되어야 한다.

## 작업 범위

- items 테이블(원청 FK, 품목명, 숨김 여부, 즐겨찾기, 최근 사용 시각)
- item_aliases 테이블(이전 이름, 변경 시각, 변경 사유)
- merged_into 컬럼으로 합쳐진 품목의 최종 품목 연결
- (원청, 품목명) 유니크 제약. 검색용 인덱스(ILIKE/trigram 등)는 실제 검색 구현이 정해지는 T-028에서 추가한다 — 지금 미리 만들면 어떤 인덱스 종류가 맞는지 모른 채 추측하게 된다

## 완료 기준

- [x] 같은 원청에 같은 이름 품목이 중복 등록되지 않는다 — 실제 중복 insert 시도 시 `unique constraint "items_client_name_active_key"` 위반 확인
- [x] 이전 이름으로도 품목을 찾는 쿼리가 동작한다 — `item_ids_in_merge_group(최종품목id)`가 옛 품목 id까지 포함해 반환함을 실제 조회로 확인(A→B 합치기 후 `item_ids_in_merge_group(B)` = {A, B})
- [x] 합쳐진 품목이 최종 품목을 가리키고 순환이 생기지 않는다 — `final_item_id(A)=B` 확인, 자기 자신에게 합치기 시도 시 `check constraint` 위반으로 차단 확인. 2단 이상 순환은 `cycle ... using path`로 방어(코드 존재, 실제 순환 데이터로는 테스트하지 않음 — 운영 DB에 순환 데이터를 만들었다가 지우는 위험을 피함)

## 주의사항

- 합치기 체인이 2단 이상 생길 수 있으므로 최종 품목을 재귀로 따라가는 함수나 뷰를 함께 만든다.
