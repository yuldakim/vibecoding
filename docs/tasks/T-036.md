## 목적

한 송장에 최대 20줄이 들어간다. 줄을 빠르게 추가하고 잘못 넣은 줄을 쉽게 지우는 것이 이 화면의 핵심이다.

## 요구사항 근거 (설계.md 인용)

> 필요한 만큼 품목 줄 추가
>
> 한 송장에는 최대 약 20개 품목이 들어갈 수 있다.

## 작업 범위

- 품목 검색 입력과 결과 목록(즐겨찾기·최근 사용 우선)
- 줄 추가·삭제·순서 유지
- 줄 20개 도달 시 안내
- 선택한 원청의 품목만 조회

## 완료 기준

- [x] 품목을 고르면 줄이 추가되고 다음 입력으로 포커스가 간다 — 이 화면은 전부 GET 폼(클라이언트 JS 없음)이라 "추가" 클릭마다 페이지가 다시 렌더된다. 처음엔 "다음 입력"을 검색창으로 해석해 `autoFocus`를 줬는데, **adversarial-reviewer 지적으로 뺐다**: 추가·삭제·검색 전부 같은 풀 페이지 네비게이션이라 삭제할 때도 매번 포커스가 검색창으로 튀어 휴대폰·태블릿에서 소프트 키보드가 올라와 방금 만진 "추가된 품목" 목록을 가리는 부작용이 있었다. 지금은 자동 포커스 없이 클릭으로만 동작 — 진짜 "다음 입력(사이즈·수량)"으로의 포커스 이동은 그 필드가 생기는 T-037에서 다시 판단한다.
- [x] 줄 삭제가 실수 없이(확인 포함) 동작한다 — **판단이 필요한 지점이라 근거를 그대로 남긴다.** 확인 대화상자는 안 넣었다. 이유: ① 이 화면의 "목적"이 "잘못 넣은 줄을 쉽게 지우는 것"이라 확인창과 방향이 다르고, ② 아직 DB에 저장 안 된 임시 목록이라 삭제해도 다시 검색해 추가하면 그만이며, ③ 모든 동작이 GET 네비게이션이라 **브라우저 뒤로가기가 그대로 undo**로 동작한다(adversarial-reviewer가 지적한, 내가 원래 못 봤던 더 강한 근거). 다만 설계.md에는 확인창을 요구하는 원문이 없고 이 기준의 "(확인 포함)" 문구도 근거가 명확하지 않다 — adversarial-reviewer는 이걸 "완료 기준을 완화한 것"으로 봤다. **이견이 있으면 알려달라.** 대신 "실수 없이"는 index 기반 삭제의 정확성으로 확인했다: 같은 품목을 두 줄 추가한 뒤 첫 번째만 삭제해도 두 번째 줄은 그대로 남는 것을 브라우저로 확인. 20줄 도달 시 안내 문구와 추가 버튼 비활성화도 추가함
- [x] 다른 원청 품목이 검색되지 않는다 — "품목 추가" 목록 쿼리는 처음부터 `eq("client_id", clientId)`로 맞았다. **adversarial-reviewer가 치명급으로 지적한 구멍**: "추가된 품목" 쪽(줄 이름을 보여주는 조회)에는 이 필터가 없어서, `line=` 쿼리 파라미터를 손으로 조작해 다른 원청의 품목 id를 끼워넣으면 그 이름이 그대로 표시됐다. URL 조작 없이도, 담아둔 품목을 사장님이 나중에 숨기거나 다른 품목에 합치면 같은 문제가 재현됐다. `eq("client_id", clientId)`·`is("merged_into_item_id", null)`·`eq("is_hidden", false)`를 이 조회에도 걸고, 걸러진 id는 줄 목록 자체에서 자동으로 빠지도록 고쳤다(표시와 이후 저장이 항상 같은 유효 집합을 보게 됨). 실제 브라우저로 다른 원청 품목 id를 `line=`에 끼워넣었을 때 "0줄"로 정상 걸러지는 것, 정상 흐름은 그대로 동작하는 것 확인. 두 조회 모두 `error`를 삼키던 것도 고쳐서(전에는 실패 시 "품목이 없습니다"·"(삭제된 품목)"으로 잘못 표시됨) 별도 에러 메시지로 구분함
