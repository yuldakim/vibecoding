# T-005 · 마이그레이션: 공장 정보·직원 계정

> 작업 상태의 SSOT는 저장소 루트의 `backlog.json`이다. 이 문서는 무엇을 왜 어떻게 만드는지만 다룬다.

| 항목 | 값 |
| --- | --- |
| 단계 | 0. 기반 구축 |
| 분류 | 데이터 모델 |
| 우선순위 | P0 |
| 예상 시간 | 30분 |
| 선행 작업 | [T-004](T-004.md) 전체 DB 스키마 설계 확정 |
| 요구사항 근거 | §2 사용자 구분, §23 공장 정보 |
| 주요 위치 | `supabase/migrations/` |

## 목적

송장·엑셀에 찍히는 공장 정보와, 비밀번호 없이 선택만으로 로그인하는 직원 계정의 저장소를 만든다.

## 요구사항 근거 (설계.md 인용)

> 사장님이 직원용 계정을 여러 개 생성할 수 있다.
>
> 직원별 작업자는 구분해서 기록하지 않고 시스템 기록에는 모두 `직원`으로 표시한다.

## 작업 범위

T-004(`docs/db-schema.md`)가 이미 확정한 설계를 그대로 적용한다 — 여기서 테이블 구조를 다시 정하지 않는다.

- `factory_settings` 테이블(공장명·대표자명·사업자등록번호·주소·전화번호·사이트 전용 이메일·사장님 비밀번호 해시·로그인 실패 횟수·잠금 시각, 단일 행 제약). `docs/db-schema.md`의 "factory_settings" 절 참고 — T-004 전에는 `factory_info`+`app_settings` 두 테이블로 가정했으나, 둘 다 "공장 전체에 하나뿐인 설정값"이라 하나로 통합됐다.
- `staff_accounts` 테이블(이름, 활성 여부, 생성일)
- 두 테이블 모두 생성과 동시에 RLS 활성화, 정책은 만들지 않음(`docs/db-schema.md` §0)
- 시드 데이터 마이그레이션

## 완료 기준

- [ ] 마이그레이션이 적용되고 롤백 없이 재적용 가능하다
- [ ] `factory_settings`가 2행 이상 들어가지 않도록 제약이 걸렸다
- [ ] 사장님 비밀번호는 평문이 아닌 해시로 저장되는 컬럼 설계다
- [ ] `factory_settings`·`staff_accounts` 둘 다 RLS가 켜져 있다(anon 키로 조회 시 빈 결과)

## 주의사항

- 직원 계정에는 비밀번호 컬럼을 두지 않는다. 설계상 직원은 선택만으로 로그인한다.
- `factory_settings`의 공장 정보 컬럼(`factory_name`·`ceo_name`·`business_reg_no`·`address`·`phone`·`site_email_address`)은 `docs/db-schema.md` §0 규칙상 NOT NULL인데, T-001(실제 공장 정보 확정)이 아직 `needs_decision`이라 진짜 값이 없다. 시드 마이그레이션에서 빈 문자열(`''`)로 1행을 채워두고, T-001이 풀리면 사장님이 설정 화면(T-019)에서 실제 값으로 덮어쓴다. `owner_password_hash`도 마찬가지로 임시 해시를 시드하고 T-001에서 실제 비밀번호로 교체한다. `updated_at`은 `default now()`를 걸어 매 insert에서 명시하지 않아도 되게 한다.
- T-003에서 `supabase link`를 아직 안 했다(T-097 `needs_decision`). 그래서 이 마이그레이션을 원격에 적용할 때 `mcp__supabase__apply_migration`을 쓰게 되는데, 이 도구가 `supabase_migrations.schema_migrations`에 기록하는 version이 로컬 `supabase/migrations/<timestamp>_공장정보_직원계정.sql` 파일명의 timestamp와 **다를 수 있다.** 나중에 T-097로 `supabase link` 후 `supabase db push`를 돌리면 CLI가 이 마이그레이션을 미적용으로 보고 재실행할 수 있으니, 적용 직후 `mcp__supabase__list_migrations`로 실제 기록된 version을 확인해서 로컬 파일명과 맞춰 둔다.
