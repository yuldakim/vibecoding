# T-022 · 원청 등록·수정 폼

> 작업 상태의 SSOT는 저장소 루트의 `backlog.json`이다. 이 문서는 무엇을 왜 어떻게 만드는지만 다룬다.

| 항목 | 값 |
| --- | --- |
| 단계 | 1. 마스터 데이터 |
| 분류 | 기능 구현 |
| 우선순위 | P0 |
| 예상 시간 | 30분 |
| 선행 작업 | [T-021](T-021.md) 원청 목록 화면 |
| 요구사항 근거 | §3 원청 관리 |
| 주요 위치 | `app/owner/clients/[id]/`, `app/owner/clients/` (등록 폼) |

## 목적

정산서 이메일이 담당자에게 정확히 가야 하므로 이메일 형식 검증이 중요하다.

## 요구사항 근거 (설계.md 인용)

> 원청별 저장 정보: 업체명, 담당자명, 담당자 이메일, 전화번호, 주소 또는 납품 장소

## 작업 범위

- 5개 기본 항목 입력·검증
- 이메일 형식 검증과 오타 경고
- 저장 후 목록 갱신
- 변경 시 audit_logs 기록

## 완료 기준

- [x] 잘못된 이메일 형식이 저장되지 않는다 — 실제 DB 원청에 `updateClient`와 동일한 검증 로직을 재현: `contact_email="abc"` → `error=invalid_email`로 거부, DB 미변경 확인
- [x] 필수 항목 누락 시 어떤 항목인지 큰 글씨로 안내된다 — `name=""` → `error=missing&fields=name` → 화면에 "다음 항목을 입력하세요: 업체명" 표시(쿼리는 고정 필드 키만 화이트리스트로 허용, 자유 텍스트 주입 아님)
- [x] 수정 내용이 즉시 반영된다 — 실제 update 실행 후 값이 바뀌는 것과 `revalidatePath("/owner/clients")`·`revalidatePath("/owner/clients/[id]")` 호출 확인. `audit_logs`에 5개 필드 전체의 before/after가 정확히 기록되는 것도 실제 insert된 행으로 확인(테스트 데이터는 정리함)
- [x] 원청을 새로 등록할 수 있다 — adversarial-reviewer가 "등록·수정 폼"인데 등록 경로가 아예 없다고 지적해 추가함. `app/owner/clients/page.tsx`에 등록 폼(`createClient`), 필수 5필드+이메일 형식+발송일/검토일(1~28) 검증 후 insert. 미입력·형식오류·저장실패 각각 에러 메시지 분리

## 주의사항

- 담당자는 원청당 한 명이라는 전제라 복수 담당자 UI를 만들지 않는다.
- 검증 실패로 되돌아왔을 때 방금 입력한 값을 잃지 않도록 `retry_*` 쿼리 파라미터로 되돌려준다(수정 폼). adversarial-reviewer 지적으로 추가 — 이전엔 전체 필드가 DB 원래값으로 리셋됐었다.
- 존재하지 않는 원청 id로 수정 요청이 오면(경합 등) 조용히 "저장했습니다"가 뜨던 문제를 막기 위해 update 전에 원청 존재를 확인한다.
