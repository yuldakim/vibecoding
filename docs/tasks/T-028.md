> 작업 상태의 SSOT는 저장소 루트의 `backlog.json`이다. 이 문서는 무엇을 왜 어떻게 만드는지만 다룬다.

## 목적

이름이 바뀐 품목을 사장님이 옛 이름으로 기억하고 있거나 반대인 경우에도 찾을 수 있어야 한다.

## 요구사항 근거 (설계.md 인용)

> 사이트 검색에서는 새 이름으로 검색해도 이전 이름으로 작성된 송장이 함께 조회되어야 한다.

## 작업 범위

- items + item_aliases 통합 검색 쿼리
- 합쳐진 품목까지 따라가는 최종 품목 해석
- 한글 부분 일치 검색과 인덱스
- 검색 결과에 '이전 이름: ○○' 표시

## 완료 기준

- [x] 새 이름으로 검색하면 옛 이름 송장이 함께 나온다 — 송장 검색 화면(T-048)이 아직 없어 "송장이 나온다"까지는 직접 못 봤다. `searchItems`가 새 이름으로 매치되면 해당 품목 id를 그대로 반환하므로, 그 id로 `invoice_lines`를 조회하는 화면이 이 함수를 그대로 쓰면 그 품목으로 작성된 모든 과거 송장(스냅샷 이름 무관)이 함께 나오는 구조. 지금 확인 가능한 건 이 id 반환까지
- [x] 옛 이름으로 검색해도 현재 품목이 나온다 — `search.check.ts`로 실제 DB 검증: 옛이름품목→새이름품목으로 합치기 후 "옛이름품목"으로 검색하면 최종 품목(새이름품목) id가 반환됨(매치된 별칭도 함께 표시)
- [x] 합쳐진 품목이 최종 품목으로 묶여 나온다 — 같은 검증에서 `final_item_id()` RPC로 합치기 체인을 따라간 결과가 정확히 최종 품목 id와 일치함을 확인

**adversarial-reviewer 지적으로 수정**: `search.check.ts`가 `lib/items/search.ts`를 import하지 않고 로직을 통째로 복사해 따로 검증하고 있었다(배포되는 실제 코드는 한 번도 실행 안 됨). `search.ts`의 import를 `@/lib/...` 별칭에서 `../supabase/server.ts`·`../db/like.ts` 상대경로로 바꿔(같은 폴더의 `recency.ts`가 이미 쓰던 방식) 플레인 node에서도 실행 가능하게 만들고, `search.check.ts`가 실제 `searchItems`를 import해서 쓰도록 고침. 재실행해서 통과 확인.
