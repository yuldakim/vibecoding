## 목적

화면 태스크마다 스타일을 새로 정하면 일관성이 깨진다. 글씨 크기·터치 영역·색 대비 기준을 먼저 컴포넌트로 고정한다.

## 요구사항 근거 (설계.md 인용)

> 주 사용자는 50대 후반의 공장 사장님과 공장 직원이다. 컴퓨터, 태블릿, 휴대폰에서 모두 사용할 수 있어야 하며, 글씨와 버튼을 크게 하고 복잡한 메뉴와 전문 용어를 최소화한다.

## 작업 범위

- 글씨 크기·간격·색 대비 토큰 정의
- 버튼 최소 높이 56px, 터치 영역 44px 이상 보장
- 입력·선택·표·모달 공통 컴포넌트
- PC/태블릿/휴대폰 3개 폭 기준 반응형 규칙
- 숫자 입력(수량·금액)용 큰 키패드 친화 입력

## 완료 기준

- [x] 공통 버튼·입력이 3개 화면 폭에서 깨지지 않는다 — 브라우저로 `/ui` 데모 확인: 버튼 줄은 `flex-wrap`으로 줄바꿈, 입력은 `w-full`, 표는 `overflow-x-auto` 컨테이너 안이라 좁은 화면에서도 페이지 자체는 가로 스크롤 안 생김(`document.documentElement.scrollWidth > clientWidth`가 false임을 JS로 직접 확인)
- [x] 본문 대비가 WCAG AA를 만족한다 — 흰 배경 기준 상대휘도 공식으로 실측: primary 5.17:1, danger 4.83:1, border 4.83:1(전부 4.5:1 이상)
- [x] 이후 화면 태스크가 이 컴포넌트만 조합해 만들 수 있다 — `/ui` 데모에서 Button(3 variant)·Input·NumberInput·Table·Dialog(네이티브 `<dialog>`, 실제로 열고 닫는 것까지 브라우저로 확인)를 조합해 송장/정산 화면과 유사한 레이아웃을 실제로 구성해봄

## 주의사항

- 전문 용어 대신 '송장 만들기', '정산서 보내기' 같은 일상어를 라벨 기본값으로 쓴다.
- `Button`은 `type="button"`이 기본값이다(스프레드보다 앞이라 호출자가 `type="submit"`으로 덮어쓸 수 있다). 리뷰에서 발견: 기본값을 안 정하면 HTML 기본(`submit`)이 그대로 적용돼, form 안의 모든 버튼("줄 추가" 같은 보조 버튼까지)이 제출 버튼이 되어 의도치 않게 송장이 확정될 수 있었다.
- `Dialog`는 `aria-labelledby`로 제목과 연결돼 있다(`useId()`로 생성). 새 prop을 추가로 만들 필요 없이 `title`만 넘기면 접근성이 자동으로 맞는다.
- `app/globals.css`의 `@theme inline` 블록은 `--color-X: var(--X)`처럼 **이름을 다르게** 유지해야 한다. `:root`와 같은 이름(`--color-X: var(--color-X)`)으로 쓰면 지금은 무해해 보여도(언레이어드가 이겨서 정상 동작) `:root` 블록이 나중에 옮겨지거나 지워지면 자기참조가 되어 값이 조용히 빈 문자열이 된다.
