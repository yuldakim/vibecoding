> 작업 상태의 SSOT는 저장소 루트의 `backlog.json`이다. 이 문서는 무엇을 왜 어떻게 만드는지만 다룬다.

| 분류 | 데이터 모델 |

| 예상 시간 | 30분 |
| 선행 작업 | [T-004](T-004.md) 전체 DB 스키마 설계 확정, [T-007](T-007.md) 마이그레이션: 품목·품목 이력, [T-008](T-008.md) 마이그레이션: 사이즈 |

## 목적

단가는 정산 금액의 근거다. 같은 조합에서 월별로 단 하나의 기본 단가만 존재하도록 강제해야 정산이 흔들리지 않는다.

## 요구사항 근거 (설계.md 인용)

> 같은 원청, 품목, 사이즈, 적용 월에서는 기본 단가가 동일하다.
>
> 단가는 부가세가 포함되지 않은 공급가액 기준이다.

## 작업 범위

- monthly_prices 테이블(원청, 품목, 사이즈, 적용 연월, 단가, 미정 여부)
- (원청, 품목, 사이즈, 적용 연월) 유니크 제약
- 단가 변경 이력 테이블(변경 전·후·시각)
- 단가는 정수(원), 공급가액 기준임을 컬럼 주석에 명시

## 완료 기준

- [x] 같은 조합의 중복 단가가 저장되지 않는다 — `unique(client_id,item_id,size_id,price_month)` 실제 중복 insert 시도 시 `23505 duplicate key` 확인
- [x] 미정 상태가 단가 null과 구분되거나 동일 규칙으로 명확히 정의됐다 — `unit_price int null`, null = 미정으로 실제 insert 성공 확인
- [x] 단가 수정 시 이력이 남는 구조다 — `price_change_history`(monthly_price_id FK, old_price/new_price, changed_by_role, changed_at) 테이블 생성. 실제 단가 수정 UI(T-051)가 없어 값이 쌓이는 것 자체는 아직 검증 못 함 — 구조만 확인

## 주의사항

- 예외 단가는 여기가 아니라 송장 줄/정산 내역에 따로 저장한다(T-057).
- RLS를 켜고 anon key로 직접 REST 호출하면 빈 배열이 오는 것까지 확인했지만, **이게 직원을 막는 실제 경로는 아니다.** 앱의 모든 서버 코드는 `lib/supabase/server.ts`의 `service_role` 클라이언트를 써서 RLS를 통째로 우회한다. 직원에게 단가가 안 보이는 진짜 이유는 T-016이 만들 "응답 DTO에서 금액 필드 제거"다. RLS는 브라우저에서 anon 키로 직접 찔러보는 경로만 막는 보조 방어선이다.
- `price_month`는 반드시 그 달 1일이어야 한다 — `monthly_prices_price_month_is_month_start` check 제약으로 강제된다(다른 날짜 insert 시 즉시 에러). T-051/T-053이 이 컬럼에 값을 넣을 때 항상 `YYYY-MM-01`로 만들어야 한다.
- `owner_login_fail_count` 같은 카운터를 앱에서 "읽고 +1 해서 쓰는" 방식으로 만들지 않는다 — 동시 요청에서 증가분이 누락된다(T-014에서 실제로 겪은 문제, `record_owner_login_failure()` 같은 단일 UPDATE RPC로 고침). 이 테이블에 향후 카운터성 컬럼을 추가하면 같은 패턴을 쓴다.
