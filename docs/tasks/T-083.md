# T-083 · 알림 생성 규칙 구현

> 작업 상태의 SSOT는 저장소 루트의 `backlog.json`이다. 이 문서는 무엇을 왜 어떻게 만드는지만 다룬다.

| 항목 | 값 |
| --- | --- |
| 단계 | 6. 알림·화면·마무리 |
| 분류 | 기능 구현 |
| 우선순위 | P0 |
| 예상 시간 | 30분 |
| 선행 작업 | [T-012](T-012.md) 마이그레이션: 변경 기록·발송 이력·알림 |
| 요구사항 근거 | §22 알림 |
| 주요 위치 | `lib/notifications/rules.ts` |

## 목적

알림이 안 뜨거나 안 사라지면 사이트 전체의 신뢰가 깨진다. 생성·해제 조건을 한 곳에 모아 관리한다.

## 작업 범위

- 사장님 알림 7종 생성 조건 정의
- 직원 알림 3종 생성 조건 정의
- 해제 조건(단가 입력 완료·승인 완료·발송 성공 등)
- 중복 알림 방지
- 알림 조회 API(역할별 필터)

## 완료 기준

- [x] 조건이 해소되면 알림이 자동으로 사라진다 — 각 `shouldNotify*` 함수가 해소된 상태(예: `resolvedAt` 채워짐, `missingPriceCount=0`, `sentAt` 채워짐)에서 `false`를 반환하는 것을 `rules.check.ts`로 확인. 실제 `is_resolved` 갱신(쓰기)은 이 판정 결과를 쓰는 후속 작업(T-078 등)의 몫 — 이 작업은 "지금 알림이 있어야 하는가"만 순수 함수로 판정한다
- [x] 같은 사건으로 알림이 중복 생성되지 않는다 — `shouldCreateNotification()`이 같은 kind+ref_type+ref_id의 미해결 알림이 있으면 false 반환, 다른 대상이거나 기존 알림이 해제됐으면 true 반환하는 것을 `rules.check.ts`로 확인
- [x] 직원 알림에 금액 정보가 들어가지 않는다 — `shouldNotifyStaffOwnerReviewNeeded`/`shouldNotifyStaffAutoSendUpcoming`/`shouldNotifyStaffSendFailed` 세 함수의 파라미터·반환 타입에 금액 필드가 아예 없다(컴파일 타임에 물리적으로 못 넣음). `getNotificationsForRole()`도 `notifications` 테이블 자체에 금액 컬럼이 없고 select 컬럼을 명시해 안전

검증: `npm run check:notifications`로 10종 규칙 + 중복방지 케이스 전부 실행해 통과 확인(`node --experimental-strip-types`). `npx tsc --noEmit` 통과.

## 주의사항

- **(리뷰에서 발견해 수정함)** `send_scheduled_date`(date 컬럼, KST 달력 날짜)를 `new Date(문자열) < new Date()`처럼 시각 있는 값과 직접 비교하면, `new Date("2026-07-25")`가 UTC 자정(=KST 09:00)으로 해석돼 **발송일 당일 오전 9시부터** 이미 지난 것으로 계산됐다(직원 "7일 전부터" 알림도 같은 이유로 경계가 9시간씩 밀림). `toKstDateString()`/`daysBetween()` 헬퍼로 두 값을 같은 종류(달력 날짜)로 맞춘 뒤 비교하도록 고쳤다. 날짜 관련 함수를 새로 추가할 때 `new Date(dateOnlyString) < new Date()`처럼 date 컬럼과 현재 시각을 직접 비교하지 않는다 — 이 저장소에 KST 관련 규약이 이 파일 말고는 아직 없다(정산 기간 1일~말일, 이월 판정도 같은 함정이 있을 수 있으니 그 작업을 할 때 다시 확인한다).
- **(리뷰에서 발견해 수정함)** `shouldNotifyFinalReviewNeeded`/`shouldNotifyRevisionReviewNeeded`가 `needs_reapproval`+`revisionNo=0`(최초 정산서가 승인 취소된 경우)을 "수정 정산서 확인 필요"로 잘못 분류했다 — §21의 "수정 정산서"는 발송 완료 후 만드는 것이라 `revisionNo=0`과는 다른 개념이다. 지금은 `revisionNo===0`이면 무조건 "최초 정산서 확인 필요" 쪽, `revisionNo>0`이면 "수정 정산서 확인 필요" 쪽으로 배타적으로 나눴다.
- `notifications`에 dedupe용 부분 유니크 인덱스(`notifications_dedupe_key` — kind + coalesce(ref_type,'') + coalesce(ref_id,-1), `is_resolved=false`인 행만)를 추가했다. `shouldCreateNotification()`은 여전히 미리보기 판정용으로 쓰고, 실제 insert 시 이 유니크 인덱스가 최종 방어선이다 — 두 경로가 동시에 판정해도 DB가 한쪽만 통과시킨다. insert 코드(T-078 등)는 이 제약 위반(`23505`)을 "이미 알림이 있다"는 정상 상황으로 처리해야 한다(에러로 취급하지 않는다).
- `shouldNotifyStaffOwnerReviewNeeded`/`shouldNotifyStaffSendFailed`는 "7일 전부터" 창을 적용하지 않는다(사건 발생형이라 날짜 파라미터가 없음, 의도적 설계) — §22 문장이 직원 3종 전체에 걸리는 수식인지 `staff_auto_send_upcoming` 하나에만 걸리는지 원문이 명확하지 않다. 다르게 읽어야 한다면 이 두 함수에 `today` 파라미터를 추가해야 한다.
- 알림 종류 10개(`rules.ts`의 함수) ↔ `notifications.kind` enum 10개 ↔ `target_role`을 잇는 매핑표가 아직 없다. T-078(발송 실패 감지)·T-084(사장님 알림 화면)·T-085(직원 알림 화면)가 각자 문자열을 다시 적게 되면 한쪽만 고쳤을 때 어긋난다 — 세 작업 중 먼저 시작하는 쪽에서 `rules.ts`에 `{fn, kind, targetRole}` 매핑 테이블을 만들어 나머지가 가져다 쓰게 한다.
