> 작업 상태의 SSOT는 저장소 루트의 `backlog.json`이다. 이 문서는 무엇을 왜 어떻게 만드는지만 다룬다.

| --- | --- |
| 단계 | 0. 기반 구축 |
| 분류 | 데이터 모델 |

| 예상 시간 | 30분 |

| 주요 위치 | `supabase/migrations/` |

## 목적

정산서는 승인·발송·수정본 재발행까지 상태가 길게 이어진다. 발송본을 덮어쓰지 않고 회차를 쌓는 구조를 처음부터 잡는다.

## 요구사항 근거 (설계.md 인용)

> 이미 발송한 정산서는 수정하거나 덮어쓰지 않는다.
>
> 승인 후 발송 전에 정산 내용을 수정하면 기존 승인 자동 취소

## 작업 범위

- settlements 테이블(원청, 정산 연월, 상태, 승인 시각, 발송 예정일, 발송 시각, 수정 회차)
- settlement_lines 테이블(송장 줄 참조, 적용 단가, 공급가액, 이월 여부, 비고)
- 합계 컬럼(전체 공급가액·부가세·최종 합계) 또는 계산 뷰 결정
- (원청, 연월, 수정 회차) 유니크 제약

## 완료 기준

- [x] 같은 원청·같은 달의 최초본과 수정본이 함께 보존된다 — `unique(client_id,period_month,revision_no)`. 실제로 같은 (client_id,period_month)에 revision_no=0(sent)과 1(draft)을 둘 다 insert해 공존 확인, 같은 revision_no 중복 시도는 `23505 duplicate key`로 차단 확인
- [x] 정산 상태 전이 값이 모두 정의됐다 — `check (status in ('draft','pending_review','approved','needs_reapproval','sent'))`. 목록 밖 값('foo') insert 시도 시 `23514 check violation` 확인
- [x] 이월 여부가 내역 줄 단위로 저장된다 — `settlement_lines.is_carried_over boolean`. 실제 insert로 true 값 저장 확인. `settlement_lines`에 `unique(settlement_id,invoice_line_id)`도 추가해 같은 정산서에 같은 송장 줄이 중복 삽입되는 것도 막음(과거 리뷰에서 발견된 문제 재발 방지)

테스트에 쓴 clients/items/invoices/invoice_lines/settlements/settlement_lines 행은 전부 삭제해 정리함.

## 주의사항

- 합계를 컬럼으로 저장하면 발송 시점 값이 고정돼 수정본 비교에 유리하다. T-081에서 이 값을 쓴다.
- `period_month`는 반드시 그 달 1일이어야 한다 — `settlements_period_month_is_month_start` check 제약으로 강제된다(리뷰에서 발견: `monthly_prices`와 똑같이 unique 제약만으로는 같은 달에 다른 날짜로 최초본이 두 개 생기는 걸 못 막아서, 같은 패턴으로 바로 추가 마이그레이션했다). T-059가 이 컬럼에 값을 넣을 때 항상 `YYYY-MM-01`로 만들어야 한다.
- `first_approved_at`·`sent_at not null` 행의 불변성은 DB가 강제하지 않는다(스키마 트리거 아님, `docs/db-schema.md` §0). T-067(정산 최종 승인)·T-080(수정 정산서 생성)이 `first_approved_at`을 절대 null로 되돌리지 않고, `sent_at`이 채워진 행을 절대 update하지 않게 애플리케이션에서 지켜야 한다.
- 리뷰 중 테스트로 `invoice_no_seq`를 실제로 소모했다(`nextval` 호출) — 실 데이터가 없는 상태라 `setval(1, false)`로 원복해뒀다. 이후로는 이 시퀀스를 테스트 목적으로 건드리지 않는다(§7: 취소된 번호는 재사용하지 않는다 — 되돌리기는 사전 오염 정리에만 예외적으로 허용).
