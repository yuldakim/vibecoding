# T-034 · 사이즈 관리(기본 4종 + 직접 입력)

> 작업 상태의 SSOT는 저장소 루트의 `backlog.json`이다. 이 문서는 무엇을 왜 어떻게 만드는지만 다룬다.

| 항목 | 값 |
| --- | --- |
| 단계 | 1. 마스터 데이터 |
| 분류 | 기능 구현 |
| 우선순위 | P1 |
| 예상 시간 | 30분 |
| 선행 작업 | [T-008](T-008.md) 마이그레이션: 사이즈 |
| 요구사항 근거 | §5 사이즈 관리 |
| 주요 위치 | `components/size-select/` |

## 목적

사이즈는 송장 작성에서 매번 쓰는 입력이다. 목록에 없는 사이즈를 그 자리에서 추가하고 다음부터는 고를 수 있어야 한다.

## 요구사항 근거 (설계.md 인용)

> 기본 사이즈: 싱글, 슈퍼싱글, 퀸, 킹
>
> 직접 입력한 사이즈는 다음 송장부터 다시 선택할 수 있다.
>
> 수량 단위는 항상 `장`으로 고정한다.

## 작업 범위

- 사이즈 선택 컴포넌트(큰 버튼형)
- 직접 입력 필드와 저장
- 중복 사이즈 이름 정규화(공백·대소문자)
- 사용 빈도순 정렬

## 완료 기준

- [x] 직접 입력한 사이즈가 다음 송장 작성 시 목록에 있다 — 아직 송장 작성 화면(T-037)이 없어 `app/(demo)/sizes/`에서 추가 후 `sizes` 테이블에 실제로 남는지, 재조회 시 목록에 뜨는지로 확인(직접 스크립트로 실제 DB 왕복 검증)
- [x] 같은 사이즈가 중복 생성되지 않는다 — 공백·대소문자 차이만 있는 이름은 `ilike` 매칭으로 기존 행을 재사용(중복 insert 없음), 실제 DB에 3가지 케이스로 검증
- [x] 수량 단위가 화면 어디서나 '장'으로 고정 표시된다 — 이 작업 범위에는 수량 입력 자체가 없음(T-037 몫). 데모 페이지에 "수량 단위는 항상 '장'" 문구만 고정 표시

## 주의사항

- "사용 빈도순 정렬"은 지금은 의미가 없다 — 송장(T-009)·송장 줄(T-037)이 없어 사이즈 사용 이력이 없다. 지금은 `sort_order, name`으로만 정렬하고, 실제 사용 데이터가 쌓인 뒤(T-037 이후) 빈도 기반 정렬을 다시 검토한다.
- `addSize` 서버 액션에 role 검사가 없다 — 아직 T-013/T-014의 세션 검증 헬퍼가 공용화되지 않아서다. 이 상태로 배포하면 인증 없이 `sizes`에 임의 행을 추가할 수 있다. T-016(RLS·서버 권한 경계) 또는 그 전에 공용 role 검사 헬퍼가 생기면 `addSize`에도 적용한다 — 배포(T-094) 전에 반드시 막혀 있어야 한다.
- 이름 중복 방지의 최종 근거는 DB(`sizes.name_normalized` 생성 컬럼 + unique 인덱스)다. `lib/sizes/actions.ts`의 trim·제로폭 제거·NFC 정규화는 사용자에게 보여줄 이름을 다듬는 전처리이고, 실제 동시성 방어는 `upsert(..., {onConflict:'name_normalized', ignoreDuplicates:true})`가 한다.
