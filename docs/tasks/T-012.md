# T-012 · 마이그레이션: 변경 기록·발송 이력·알림

> 작업 상태의 SSOT는 저장소 루트의 `backlog.json`이다. 이 문서는 무엇을 왜 어떻게 만드는지만 다룬다.

| 항목 | 값 |
| --- | --- |
| 단계 | 0. 기반 구축 |
| 분류 | 데이터 모델 |
| 우선순위 | P1 |
| 예상 시간 | 30분 |
| 선행 작업 | [T-004](T-004.md) 전체 DB 스키마 설계 확정 |
| 요구사항 근거 | §8 출력과 취소, §20 발송 실패 처리, §22 알림 |
| 주요 위치 | `supabase/migrations/` |

## 목적

'내부에는 시각과 변경 전후만 기록한다'는 요구를 만족시키고, 발송 실패 알림을 화면에 띄울 근거 데이터를 만든다.

## 요구사항 근거 (설계.md 인용)

> 내부에는 작성 시각, 출력 시각, 재출력 시각, 취소 시각, 변경 전후 내용만 기록한다.
>
> 재발송에 성공하면 알림을 자동으로 해제한다.

## 작업 범위

- audit_logs 테이블(대상 종류·대상 id·행위·변경 전·변경 후·행위자 역할·시각)
- email_logs 테이블(원청, 종류, 파일명, 성공 여부, 실패 사유, 시각)
- notifications 테이블(종류, 대상 역할, 참조 id, 해제 여부)
- 행위자는 '직원' 또는 '사장님' 두 값만 저장

## 완료 기준

- [x] 직원 개인을 식별하는 값이 audit_logs에 저장되지 않는다 — `actor_role text check (in ('staff','owner'))`뿐, 계정 id·이름 컬럼 없음
- [x] 발송 실패 사유가 문자열로 보존된다 — `email_logs.failure_reason text null`, `success=false`일 때 채워짐
- [x] 알림이 해제 가능한 구조다 — `notifications.is_resolved boolean default false` + `resolved_at timestamptz null`

검증(실제 DB, 테스트 데이터는 삭제해 정리함): actor_role='manager' insert → check violation. email_logs.kind='spam_blast' insert → check violation, 'price_check_request'는 성공. notifications.kind='bogus_kind' insert → check violation, 'owner_price_missing'은 성공. 세 테이블 모두 `pg_class.relrowsecurity=true` 확인.

## 주의사항

- 설계상 직원별 활동 추적은 1차 범위에서 제외다. 계정 id를 로그에 남기지 않는다.
