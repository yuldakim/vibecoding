## 목적

태블릿에서 쓰다 사무실 PC에서 마무리하는 사용 방식을 지원한다. 임시 송장은 번호가 없고 누구나 고칠 수 있다.

## 요구사항 근거 (설계.md 인용)

> 임시 송장: 송장번호가 없음, 어느 기기에서든 이어서 작성 가능, 모든 직원이 수정 가능, 자유롭게 삭제 가능

## 작업 범위

- 임시 저장 버튼과 자동 저장(입력 중 주기 저장)
- 번호 없이 draft 상태로 저장
- 다른 기기에서 열어 이어쓰기
- 동시 편집 시 마지막 저장 우선 규칙과 안내

## 완료 기준

- [x] A 기기에서 저장한 임시 송장이 B 기기에서 열린다 — 브라우저로 실제 확인: 사이즈를 퀸으로, 수량을 7로 저장한 뒤 같은 URL(`/invoices/new/[id]`)에 완전히 새로 접속(다른 기기를 흉내낸 새 요청) → 퀸·7장이 그대로 열림
- [x] 임시 송장에 송장번호가 없다 — `invoices.invoice_no`를 아예 안 넣고 insert(`status: "draft"`만 지정). DB 체크 제약(`status='draft' → invoice_no IS NULL`)이 이중으로 강제. 실제 DB로 `invoice_no: null` 확인
- [x] 저장 실패 시 사용자에게 분명히 알린다 — `updateLine`·`deleteLine` 모두 실패 시 `{ok:false, error:"..."}`를 돌려주고 `LineRow`가 그 문구를 그대로 화면에 띄운다(리뷰 전엔 `deleteLine`이 실패를 삼키고 조용히 아무 반응이 없었다 — 고침). `addLine`은 검증 실패마다 다른 에러 코드로 리다이렉트해 문구를 구분해서 보여준다

**설계를 T-036/T-037의 URL 인코딩 방식에서 완전히 바꿨다.** 기존엔 "줄"이 `/invoices/new?line=itemId:sizeId:qty:lineKey` 같은 URL 쿼리 상태였다 — 어느 기기에서든 이어서 작성하려면 URL 자체를 공유해야 하는데, 이 작업의 요구사항("서버에 임시 저장")과 맞지 않는다. 그래서 원청을 고르는 순간 `invoices` 행(`status='draft'`)을 실제로 만들고, 그 뒤로는 품목 추가·삭제·사이즈·수량 변경이 전부 `invoice_lines`에 즉시 반영되는 서버 액션이 됐다. 부수 효과로 T-037에서 몇 차례 리뷰를 거쳐 겨우 잡았던 "줄 순서가 바뀌면 다른 줄의 입력 상태가 섞이는" 버그 클래스 자체가 사라졌다 — React key가 이제 DB가 부여한 진짜 `invoice_lines.id`라 재사용되거나 위치가 밀릴 일이 없다. 기존 `app/invoices/new/line-editor.tsx`·`line-row-editor.tsx`·`line-codec.ts`(+check)는 전부 지우고 `app/invoices/new/[id]/` 아래로 새로 만들었다.

**"자동 저장(입력 중 주기 저장)"과 "동시 편집 시 마지막 저장 우선"에 대한 판단**: 별도의 디바운스 자동저장 타이머는 안 만들었다. 사이즈·수량을 "저장" 누르는 순간 곧바로 DB에 쓰이므로 매 조작이 곧 자동 저장이다. "마지막 저장 우선"도 그냥 같은 행을 UPDATE하는 것으로 자연히 충족된다(나중에 쓴 값이 남는다) — 별도의 충돌 안내 배너는 만들지 않았다. 두 사람이 동시에 같은 줄을 고치는 상황은 이 공장의 실사용 규모(직원 소수)에서 위험 대비 구현 비용이 안 맞는다고 판단했다.
  - **정정 (adversarial-reviewer 지적)**: "잃어버릴 로컬 상태가 애초에 없다"는 원래 서술이 틀렸다 — `LineRow`에서 사이즈·수량을 바꾸고 "저장"을 누르기 전까지는 화면 값과 DB 값이 다른 상태가 실제로 존재한다(예: 수량을 고치고 저장 없이 다른 페이지로 이동하면 화면은 새 값을 보였지만 DB는 옛 값 그대로). "저장" 버튼 옆에 화면 값이 DB 값과 다를 때 "아직 저장 안 됨" 문구를 띄우는 최소한의 표시를 추가해 이 간극을 사용자에게 알린다.

## 주의사항

- 임시 송장 **전체**(원청·모든 줄) 삭제(T-042 몫)는 `invoice_lines`에 `on delete cascade`가 없다(확정 송장을 실수로 캐스케이드 삭제하는 걸 막으려는 의도적 설계, `docs/db-schema.md` 참고). 그래서 삭제할 때 `invoice_lines`를 먼저 지우고 `invoices`를 지워야 하며, 이 둘은 하나의 트랜잭션으로 묶는다 — 순서를 바꾸면 FK 위반으로 실패하고(안전하게 실패), 트랜잭션 없이 나눠서 하면 중간에 실패 시 줄만 사라진 빈 임시 송장이 남을 수 있다. **이번 작업은 줄 하나만 지우는 것까지만 다뤘다**(단일 행 delete라 트랜잭션이 필요 없음) — 임시 송장 전체 삭제는 T-042에서 위 순서를 지켜 구현해야 한다.
- 납품 날짜는 지금 "오늘(KST)"로 고정 저장된다. 실제로 바꾸는 UI는 T-040 몫이다.
- **T-044(송장 확정) 전에 반드시 닫아야 할 것 — `updateLine`/`deleteLine`의 draft 상태 확인이 별도 SELECT 뒤에 이어지는 UPDATE/DELETE라 TOCTOU(확인-후-변경 사이 경합)가 존재한다.** 지금은 "확정" 자체가 없어 이 경합을 트리거할 코드 경로가 없으므로 무해하지만, T-044가 확정 액션을 추가하면 "확인 시점엔 draft였지만 그 직후 다른 탭에서 확정된" 송장의 줄이 그대로 수정/삭제될 수 있다 — §8 "출력한 송장은 수정할 수 없다" 위반. T-044를 만들 때 이 두 함수(또는 확정 액션 자체)가 원자적으로 상태를 확인하도록 같이 고쳐야 한다(예: `UPDATE ... WHERE id=? AND invoice_id IN (SELECT id FROM invoices WHERE status='draft')`처럼 조건부 UPDATE로 바꾸거나, DB 트랜잭션/락으로 확정과 줄 수정이 겹치지 않게 함).
- **T-044가 결정해야 할 것 — `item_name_snapshot`은 지금 "줄을 추가하는 순간"의 품목명으로 굳는다.** 임시 송장이 열려 있는 동안 그 품목이 사장님에 의해 이름 변경·합치기(T-032/T-033) 되면, 화면과 DB는 옛 이름을 계속 보여주고 아무 표시도 없다. 이대로 확정하면 인쇄물엔 옛 이름이 남고, 나중에 정산서 엑셀은 "최종 품목명"을 쓰므로(§4) 같은 줄인데 인쇄본과 정산서의 이름이 영구히 달라질 수 있다. T-044는 이 중 하나를 명시적으로 정해야 한다: (a) 확정 시점에 `item_id`로 최신 이름을 다시 조회해 `item_name_snapshot`을 갱신하거나, (b) 추가 시점 스냅샷을 그대로 신뢰하고 문서화한다. 지금은 어느 쪽도 결정되지 않은 상태다.

**adversarial-reviewer 1차 리뷰(치명 0 / 중요 6) 반영 내역**:
1. `LineRow`의 `key`를 `line.id`뿐 아니라 `size_id`·`quantity`까지 합친 `${line.id}:${line.size_id}:${line.quantity}`로 바꿔, 이 줄 자신의 서버 값이 다른 기기/탭에서 바뀌어도 항상 리마운트되게 함(T-037류 stale-state 버그의 재발). `page.tsx`에서 고침.
2. 위 "자동 저장" 서술의 오류를 정정하고, `LineRow`에 "아직 저장 안 됨" 표시를 추가함(사이즈·수량을 바꾸고 저장을 안 누른 상태를 화면 값 vs. props 비교로 감지). 브라우저로 확인: 사이즈를 싱글→퀸으로 바꾸자 즉시 빨간 "아직 저장 안 됨" 문구가 뜨고, 저장을 누르자 사라짐(동시에 DB `invoice_lines.size_id`가 실제로 3으로 바뀐 것을 SQL로 확인).
3. `updateLine`/`deleteLine`의 draft 상태 확인 TOCTOU는 코드로 안 고치고 위 "주의사항"에 T-044 전에 닫아야 할 항목으로 문서화함(지금은 확정 액션이 없어 무해).
4. "20줄 도달" 안내를 `atMax`일 때 무조건 뜨는 배너로 추가함(`page.tsx`).
5. `deleteLine`이 `Promise<DeleteLineResult>`를 돌려주도록 바꿔 실패를 삼키지 않게 함. 브라우저로 확인: DB에서 줄을 먼저 지운 뒤(다른 기기가 먼저 지운 상황을 흉내냄) 화면에서 같은 줄의 "삭제"를 누르자 "이미 지워졌거나 확정된 줄입니다. 새로고침 후 확인하세요."가 표시됨(이전엔 조용히 아무 반응 없었음).
6. `item_name_snapshot`의 스냅샷 시점(추가 시 vs. 확정 시) 문제는 코드로 안 고치고 위 "주의사항"에 T-044가 결정할 항목으로 문서화함.

부수적으로 `MAX_LINES`/`MAX_QUANTITY`를 `actions.ts`("use server" 파일)에서 값으로 export하고 있었는데, Next.js 서버 액션 모듈은 async 함수가 아닌 값을 export할 수 없어 빌드가 깨졌다(`npm run build` 시 "The module has no exports at all"로 발견) — 두 상수를 별도 파일 `app/invoices/new/[id]/constants.ts`로 분리해 고침.

검증(2차): `npx tsc --noEmit`·`npm run lint`·`npm run build` 모두 통과. 줄 수 한도 내(`page.tsx` 158줄, `actions.ts` 117줄, `line-row.tsx` 85줄, `constants.ts` 2줄 — 모두 200줄 한도 이내). 브라우저로 위 2·5번 시나리오 실제 확인 후 테스트 데이터(원청·품목·직원 계정·임시 송장) 정리 완료.
