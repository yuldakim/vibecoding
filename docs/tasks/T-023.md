# T-023 · 원청별 정산 일정 설정

> 작업 상태의 SSOT는 저장소 루트의 `backlog.json`이다. 이 문서는 무엇을 왜 어떻게 만드는지만 다룬다.

| 항목 | 값 |
| --- | --- |
| 단계 | 1. 마스터 데이터 |
| 분류 | 기능 구현 |
| 우선순위 | P1 |
| 예상 시간 | 30분 |
| 선행 작업 | [T-022](T-022.md) 원청 등록·수정 폼 |
| 요구사항 근거 | §3 원청 관리, §16 정산 승인과 자동 발송, §22 알림 |
| 주요 위치 | `app/owner/clients/[id]/schedule/` |

## 목적

자동 발송 스케줄러와 알림 표시 시점이 모두 이 두 값에서 나온다.

## 작업 범위

- 자동 발송일(매월 N일) 선택 UI
- 확인 요청 기준일 선택 UI
- 두 날짜 관계 검증(확인 요청일이 발송일보다 앞)
- 설정값 미리보기 문장 표시

## 완료 기준

- [x] 발송일·기준일이 저장되고 원청 목록에 표시된다 — 브라우저로 저장 확인. **adversarial-reviewer 지적으로 수정**: 원청 목록(`app/owner/clients/page.tsx`)이 `owner_review_day`를 조회·표시하지 않아서 저장은 되는데 목록에서 안 보였다. select에 컬럼 추가하고 "매월 N일 발송 · N일부터 확인" 형태로 표/카드 둘 다에 표시하도록 고침
- [x] 기준일이 발송일보다 뒤면 저장이 막힌다 — 브라우저로 실제 확인(15>=10 조합 거부, 에러 메시지와 함께 입력값 유지). **adversarial-reviewer 지적으로 수정 2가지**: ① 검증 실패 시 입력값이 DB 원래값으로 리셋되던 버그를 `retry_*` 쿼리 파라미터로 고침. ② 원청 등록 폼(`createClient`)에는 이 교차검증이 아예 없어서, 등록 단계에서 이미 "검토일>=발송일"인 원청이 만들어질 수 있었다 — `createClient`에도 같은 검증을 추가함
- [x] '매월 10일에 자동 발송, 5일부터 확인 요청' 형태의 안내 문장이 보인다 — 브라우저로 확인

## 주의사항

- 말일이 없는 달(29·30·31일 설정) 처리 규칙은 T-075에서 구현한다. 여기서는 안내 문구로 알린다. adversarial-reviewer 확인: 지금 이 값을 읽는 코드는 표시용 3곳뿐이라 당장은 죽은 코드가 맞다.
- **발송일은 2일 이상이어야 한다.** 검토 기준일 최소값이 1일이라, 발송일이 1일이면 "검토일 < 발송일"을 만족하는 값이 존재하지 않아 저장이 영원히 막히는 막다른 조합이 된다(adversarial-reviewer 지적으로 발견, `createClient`·`updateSchedule` 양쪽에 발송일 최소값을 2로 올려서 고침).

## 쉬운 설명

원청 상세 페이지에 "정산 일정 설정" 하위 화면을 만든다. `clients` 테이블에는
이미 `auto_send_day`(발송일)·`owner_review_day`(검토 기준일) 컬럼이 있고
T-022 등록 폼이 이미 채우고 있다. 이 작업은 그 두 값을 별도로 수정하는
화면과, "검토 기준일이 발송일보다 앞서야 한다"는 새 교차검증만 추가한다.

## 관련 파일

- `app/owner/clients/[id]/page.tsx` — 원청 상세(수정 폼). 여기에 하위 화면
  링크만 추가한다.
- `app/owner/clients/actions.ts` — `createClient`의 `isValidDay` 검증 패턴
  참고(1~28 범위).
- 새로 만들 것: `app/owner/clients/[id]/schedule/page.tsx`,
  `app/owner/clients/[id]/schedule/actions.ts`
