## 목적

같은 제품이 조금씩 다른 이름으로 여러 개 등록된 상황을 정리한다. 합친 뒤에는 정산서에 최종 이름 하나만 나와야 한다.

## 요구사항 근거 (설계.md 인용)

> 여러 품목을 하나의 최종 품목으로 합치기
>
> 이전 이름은 원청에 보내는 엑셀에 표시하지 않는다.

## 작업 범위

- 합칠 품목 다중 선택과 최종 품목 지정
- merged_into 설정과 합치기 체인 해석
- 합치기 전 영향 미리보기(송장 수·정산 영향)
- 되돌리기 불가 경고와 확인 절차

## 완료 기준

- [x] 합친 후 정산서에 최종 품목명 하나로 표시된다 — 정산서 엑셀(T-072)이 아직 없어 직접 확인 불가. `mergeItems`가 `items.merged_into_item_id`만 세팅하고 이름 자체는 최종 품목 것 그대로 유지되는 구조를 브라우저+DB로 확인. **완전한 충족은 T-072 구현 시 재확인 필요**
- [x] 과거 송장에는 각자의 당시 이름이 남는다 — `invoice_lines.item_name_snapshot`을 이 기능이 전혀 건드리지 않음을 실제 DB로 확인(합치기 전후 스냅샷 값 동일)
- [x] 합치기 체인이 2단이어도 최종 품목이 정확히 해석된다 — A→C→D로 2단 합치기 실행 후 `final_item_id(A)`·`final_item_id(C)` 둘 다 D로 정확히 resolve되는 것을 Postgres 함수로 직접 확인. `searchItems`로 A의 옛 이름 검색 시 D가 반환되는 것도 확인

**adversarial-reviewer가 치명으로 지적해 추가한 것**: 합치기 자체는 `monthly_prices`를 안 건드리지만, T-056이 이미 "합쳐진 품목은 최종 품목 단가로 해석"하기로 완료 기준에 정해뒀다(`docs/tasks/T-056.md`). 즉 합친 뒤 T-056이 구현되면, 이미 확정된 과거 송장 줄의 적용 단가가 조용히 바뀔 수 있다 — 사장님은 지금 이 화면에서 그 사실을 전혀 알 수 없었다. `app/owner/items/merge/price-impact.ts`(`findPriceConflicts`)를 추가해, 소스 품목이 확정 송장에 쓰인 달·사이즈 조합마다 소스 단가와 최종 품목 단가를 비교하고 다르면 미리보기에 빨간 경고로 표시하도록 고침(합치기 자체를 막지는 않되 판단 근거를 줌). 실제 브라우저로 12,000원→15,000원 경고가 뜨는 것 확인.

## 주의사항

- 단가는 품목별로 따로 있으므로 합친 뒤 단가 충돌 처리 규칙을 T-056에서 함께 확인한다. → 위 완료 기준에 적은 대로 미리보기 경고로 1차 대응함.
- **adversarial-reviewer 지적으로 수정한 것들**:
  - 숨긴 품목이 합치기 후보 목록에 섞여 있어서, 숨긴 품목을 최종으로 고르면 합쳐진 품목이 품목 관리 기본 화면에서 통째로 안 보이게 되는 문제 — 합치기 후보에서 `is_hidden=true` 품목을 제외함
  - 소스 품목 여러 개 중 일부만 합쳐지고 중간에 실패하면 "합치기에 실패했습니다"로만 떠서 이미 합쳐진 게 있다는 걸 사장님이 모르는 문제 — 실패 시 몇 개가 이미 합쳐졌는지 세어 메시지에 포함하도록 수정
  - `docs/tasks/T-068.md`(승인 후 수정 시 승인 자동 취소)의 변경 감지 대상에 "품목 합치기"가 빠져 있어서 기록해 둠(지금 당장 코드로 막을 필요는 없음 — T-067/T-068이 아직 없음)

## 쉬운 설명

같은 제품이 조금씩 다른 이름으로 여러 개 등록되는 상황을 정리하는 작업이다. 예를 들어 "퀸 차렵이불 면"과 "퀸 면 차렵"이 사실 같은 제품인데 이름만 다르게 등록돼 있을 수 있다. 합치기를 진행하면 정산서는 최종 이름 하나만 표시되지만, 과거에 쓴 송장에는 각각 당시 이름이 그대로 남아 기록으로 보존된다. 합치기는 되돌릴 수 없으므로 미리보기 화면에서 영향받을 송장 건수나 정산 내역을 확인한 후 경고 문구를 보고 진행해야 한다.
