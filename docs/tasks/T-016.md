> 작업 상태의 SSOT는 저장소 루트의 `backlog.json`이다. 이 문서는 무엇을 왜 어떻게 만드는지만 다룬다.

## 목적

화면에서 감추는 것만으로는 부족하다. 직원 세션으로 API를 직접 호출해도 단가·공급가액·정산 총액이 나오지 않아야 한다.

## 요구사항 근거 (설계.md 인용)

> 직원에게 숨기는 정보: 봉제 단가, 공급가액, 부가세, 정산 총금액, 정산서 상세 내용

## 작업 범위

- ~~monthly_prices·settlements·settlement_lines에 역할 기반 접근 제한~~ — T-010·T-011에서 이미 끝남(RLS 활성화 + 정책 0개 = anon/authenticated 전면 차단, `docs/db-schema.md` §0). 이 앱은 Supabase Auth를 안 쓰고 서버 코드가 전부 `service_role`을 쓰므로, DB에 새 정책을 추가하는 건 범위가 아니다 — 실제 방어선은 아래 두 항목이다.
- 서버 액션·라우트 핸들러 공통 역할 검사 헬퍼 — `lib/auth/requireRole()`
- 직원 응답 DTO에서 금액 필드 제거 — `lib/auth/redactMoneyFields()`
- 권한 위반 시 403 처리 — `lib/auth/toForbiddenResponse()`. 화면 안내는 T-018(역할별 네비게이션과 라우트 가드)에서 다룬다.

## 완료 기준

- [x] (수정) 직원 세션으로 단가 조회를 시도하면 거부된다 — `requireRole('owner')`가 staff 세션에서 `ForbiddenError`를 던지는 것을 `lib/auth/authorize.check.ts`로 검증(순수 판정 로직 `satisfiesRole`을 `encodeSession`/`decodeSession` 왕복으로 실제 확인). **단가·정산을 실제로 읽는 API/화면이 아직 없어(T-051/T-059/T-062 미착수) "호출하면 403이 온다"는 문자 그대로는 검증 못 함** — 그 화면들이 만들어질 때 `requireRole('owner')`를 맨 앞에 붙이기만 하면 된다.
- [x] (수정) 직원 화면 응답에 금액 필드가 키 자체로도 안 남는다 — `redactMoneyFields(data, fields, role)`가 staff role일 때 지정 필드를 `delete`로 제거하는 것을 확인(값을 null/0으로 두는 방식이 아니라 키 자체 제거). 소비할 화면이 없어 실제 네트워크 탭 확인은 못 함 — 같은 이유로 뒤로 미룸.
- [x] 사장님 세션에서는 정상 동작한다 — `satisfiesRole(ownerSession, 'staff')`도 true(사장님은 직원 권한 포함), `redactMoneyFields(data, fields, 'owner')`는 원본 그대로 반환됨을 확인.

## 주의사항

- 네트워크 탭에 금액이 실려 오면 실패다. 화면 숨김이 아니라 응답에서 빼야 한다.
- **후속 작업 필수**: T-051(월별 단가 관리 화면)·T-059(월말 정산 내역 자동 생성)·T-062(정산 상세 표 화면) 등 단가·정산을 실제로 읽는 서버 액션/라우트 핸들러는 맨 앞에 `await requireRole('owner')`(또는 필요한 role)를 반드시 붙이고, 직원에게 보내는 응답은 `redactMoneyFields()`를 거쳐야 한다. 이 헬퍼는 "만들어만 두고 아무도 안 쓰면" 무의미하다 — 각 화면 작업의 완료 기준에 "requireRole/redactMoneyFields를 썼는가"를 포함시킬 것.
- `lib/auth/authorize.ts`는 Next.js 의존성이 없는 순수 함수라 `node --experimental-strip-types`로 직접 실행 검증 가능하다(`lib/auth/session-guard.ts`는 `next/headers`를 쓰므로 Next 런타임 밖에서 못 돈다 — 그래서 판정 로직을 분리했다). `npm run check:auth`로 실행한다.
- `redactMoneyFields`는 **얕은 delete만** 한다. 최상위 키만 지운다 — 정산 상세처럼 `settlement_lines[].applied_unit_price` 같은 중첩 금액에는 안 먹힌다. 재귀로 확장하지 말고, 직원 세션일 때는 애초에 그 컬럼을 select하지 않는 것으로 막는다.
- **(리뷰에서 발견해 수정함)** `requireRole`이 쿠키만 디코드하고 끝나면 `docs/db-schema.md` §0("매 요청마다 staff_accounts.is_active만 재확인한다")을 어긴다 — 사장님이 근무 중인 직원을 사용 중지시켜도 세션 TTL(12시간) 동안 계속 통과했다. 지금은 `requireRole`이 staff 세션이면 매번 DB로 `is_active`를 다시 확인한다(브라우저로 재현: 로그인 상태에서 DB로 계정을 비활성화하고 새로고침하면 즉시 `/select`로 튕겨나가는 것 확인함).
- **(리뷰에서 발견해 수정함)** `app/(staff)/home/page.tsx`·`app/(owner-area)/owner-home/page.tsx`가 원래 `decodeSession`을 각자 직접 불러 `session.role !== 'staff'`처럼 자체 판정을 했다 — `satisfiesRole`(사장님은 직원 권한도 포함)과 다른 결론을 내서 사장님이 `/home`에 못 들어갔다. 지금은 두 페이지 다 `getSessionForRole()`(session-guard.ts에 새로 추가, requireRole을 감싸 페이지에서 쓰기 좋게 null을 반환)을 쓴다. 앞으로 role 판정이 필요한 페이지는 전부 이걸 써야 한다 — `decodeSession`을 페이지에서 직접 부르지 않는다.
