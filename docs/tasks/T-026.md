## 목적

한 원청에 100개 이상 품목이 쌓이므로 목록 자체가 검색과 정렬을 갖춰야 쓸 수 있다.

## 요구사항 근거 (설계.md 인용)

> 품목은 원청별로 따로 관리한다. 한 원청에 50~100개 이상의 품목이 등록될 수 있다.

## 작업 범위

- 원청 선택 후 품목 목록 표시
- 품목명 검색 입력
- 숨김 품목 포함/제외 토글
- 즐겨찾기·최근 사용 표시

## 완료 기준

- [x] 품목 100개에서 검색이 즉각 반응한다 — GET 폼(서버 컴포넌트 재조회) 방식, JS 없이 "필터 적용" 제출로 동작. 원청 1곳에 품목 100개(숨김 5개, 즐겨찾기 포함, 합쳐진 품목 1개 섞음) 만들어 검색 조건 실제 쿼리로 확인(결과 정확)
- [x] 숨김 품목이 기본 목록에서 빠진다 — 실제 데이터로 확인: 기본 94개(100-숨김5-합쳐짐1), "숨긴 품목도 보기" 체크 시 99개(합쳐진 것만 제외)
- [x] 다른 원청의 품목이 섞이지 않는다 — `client_id` 필터로 원청 A 조회 시 원청 B의 품목 0건 확인. 합쳐진 품목(`merged_into_item_id not null`)도 목록에서 제외 확인(완료 기준엔 없었지만 §4 요구사항상 필요해서 추가 검증)

테스트 데이터(원청 2곳, 품목 102개)는 검증 후 전부 삭제해 정리함.

## 주의사항

- **(리뷰에서 발견해 수정함)** `last_used_at`을 `new Date(...).toLocaleDateString("ko-KR")`로 표시했는데, 서버가 UTC로 돌면 KST 오후~자정 사이 시각이 하루 다르게 표시되는 버그가 있었다. `lib/date/kst.ts`의 `formatKstDate()`로 고쳤다.
- 검색어의 `%`/`_` LIKE 와일드카드 이스케이프를 `lib/db/like.ts`의 `escapeLike()`로 통일했다(원청 목록(T-021)과 공유 — 화면마다 따로 만들면 같은 입력에 화면마다 다른 결과가 나온다).
- `clientId` 쿼리 파라미터가 정수가 아니면(예: 손타이핑) 조용히 빈 화면이 되던 것을 `Number.isInteger()` 검사로 기본 원청으로 안전하게 되돌리게 했다. 조회 자체가 실패하면 "조건에 맞는 품목이 없습니다" 대신 별도 에러 문구를 보여준다.
