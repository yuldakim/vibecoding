# 서브에이전트

이 프로젝트에는 전용 서브에이전트 둘이 있다. `.claude/agents/`에 정의돼 있다.

| 에이전트 | 모델 | 언제 | 도구 |
| --- | --- | --- | --- |
| `task-briefer` | Haiku | 작업 **시작 전** | 읽기 + 태스크 문서 쓰기 |
| `adversarial-reviewer` | Opus | 파일을 만들거나 고친 **뒤** | 읽기 전용 |

앞은 싸고 빠른 정찰, 뒤는 비싸고 깊은 반박이다. 역할을 바꾸지 않는다 —
정찰에 Opus를 쓰면 돈이 새고, 리뷰를 Haiku에 맡기면 놓친다.

---

## task-briefer — 시작 전 정찰

```
Agent(subagent_type: "task-briefer", prompt: "T-044 작업을 시작한다. 브리핑해줘.")
```

**하는 일**

1. `node tools/backlog.mjs get <id>`로 작업 정보를 읽는다.
2. 요구사항 근거 절을 `설계.md`에서 찾아 읽는다.
3. 주요 위치·선행 작업 산출물·도메인 키워드로 저장소를 뒤진다.
4. `docs/tasks/<id>.md` 끝에 `## 쉬운 설명`과 `## 관련 파일`을 붙인다.
   (있으면 그 부분만 교체한다. 위쪽 내용은 건드리지 않는다)
5. 짧은 브리핑을 돌려준다.

**언제 부르나**

- 새 백로그 작업을 시작할 때 — **기본적으로 항상.**
- 사용자가 "N번 작업 브리핑", "이거 뭐부터 봐야 해"라고 할 때.

순서는 `브리핑 → set <id> 진행 → 작업`이다. 브리핑은 정찰이라 상태를 바꾸기
전에 해도 되지만, **브리핑 결과를 보고 실제로 착수하기로 했으면 코드를 건드리기
전에 반드시 `in_progress`로 바꾼다.** 브리핑만 받고 작업은 안 하기로 했다면
상태는 `todo`로 둔다.

**안 불러도 되는 때**

- 이미 그 작업을 하는 중이고 맥락이 다 있을 때.
- `docs/tasks/<id>.md`에 `## 관련 파일`이 이미 있고 저장소가 그 뒤로 안 바뀌었을 때.
- 한 줄 수정이나 오타 고치기.

**결과를 어떻게 다루나**

브리핑은 **정찰 결과지 설계가 아니다.** "만들 파일" 목록은 제안이고, 실제
구조는 작업하면서 정한다. 다만 "이미 있는 파일"은 실제로 확인된 것이므로
같은 것을 다시 만들지 않는다.

Haiku는 경로를 지어낼 수 있다. 브리핑이 가리킨 파일을 실제로 열었는데 없으면
그 브리핑 항목을 버리고 직접 찾는다.

## adversarial-reviewer — 끝난 뒤 반박

```
Agent(subagent_type: "adversarial-reviewer",
      prompt: "T-060 정산 계산 로직을 구현했다. lib/settlements/calc.ts와 테스트를 만들었다. 반박해줘.")
```

작업 id와 무엇을 했는지를 함께 넘긴다. 무엇을 하기로 한 작업인지 알아야
완료 기준과 대조할 수 있다.

**보는 것** (위쪽이 더 치명적)

1. 도메인 불변식 위반 — 부가세·송장번호·품목명·이월·권한·삭제 금지
2. 완료 기준 미충족
3. 정확성 버그 — 동시성, 경계 날짜, null·미정 단가, 트랜잭션
4. 범위 초과와 구조 — 1차 제외 기능, 줄 수 한도, 중복 로직

**언제 부르나 — 필수**

- 백로그 작업을 `done`으로 바꾸기 **직전**. 예외 없다.
- 돈 계산(`lib/settlements/`, `lib/prices/`), 송장번호 부여, 권한 경계,
  마이그레이션을 건드렸을 때는 작업 중간에도 한 번 부른다.
- 되돌리기 어려운 것(마이그레이션 적용, 발송, 품목 합치기)을 실행하기 전.

**안 불러도 되는 때**

- 문서만 고쳤을 때.
- 설정 파일 한 줄 수정.
- 아직 만드는 중이고 다음 턴에 계속할 때 — 완성된 뒤에 한 번 부른다.

매 파일 편집마다 부르지 않는다. 작업 단위가 끝났을 때 한 번이다.

**결과를 어떻게 다루나**

| 등급 | 어떻게 |
| --- | --- |
| 치명 | **반드시 고친다.** 안 고칠 거면 done으로 넘기지 않는다. |
| 중요 | 고친다. 못 고칠 사정이 있으면 백로그에 새 작업으로 등록한다. |
| 제안 | 판단해서 취한다. 안 취해도 된다. |

- **리뷰어는 동료지 권위가 아니다.** 지적이 틀렸다고 판단되면 근거를 들어
  반박하고 그대로 간다. 다만 *왜 틀렸는지*를 사용자 보고에 남긴다.
- 지적을 반영했으면 **무엇을 어떻게 고쳤는지** 보고에 쓴다. "리뷰 반영함"은
  보고가 아니다.
- 리뷰어가 "확인 못 함"으로 남긴 영역이 있으면 그대로 넘기지 말고, 중요한
  영역이면 직접 보거나 다시 위임한다.

**리뷰어를 속이지 않는다.** 검증 전에 커밋해서 diff를 비우거나, 문제가 있는
파일을 빼고 일부만 보여주지 않는다. 리뷰를 통과하는 것이 목적이 아니라
틀린 것을 찾는 것이 목적이다.

## 둘 다 지키는 것

- `backlog.json`을 직접 읽지 않는다. 둘 다 CLI를 쓰도록 만들어져 있다.
- 리뷰어는 **고치지 않는다.** 편집 도구를 주지 않았다. 고치는 것은 메인
  에이전트 일이다 — 리뷰어가 직접 고치면 누가 검증하는지가 사라진다.
- 서브에이전트의 보고는 사용자에게 그대로 전달되지 않는다. 메인 에이전트가
  **무엇이 중요한지 추려서** 보고한다.
