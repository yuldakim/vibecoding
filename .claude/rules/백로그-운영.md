# 백로그 운영

작업 상태의 SSOT는 `backlog.json`이다. **직접 열지도 고치지도 않는다** —
hook이 Read·Edit·Write는 물론 `cat`·`jq`·`sed` 같은 셸 우회까지 막는다.
96개 태스크가 통째로 컨텍스트에 실리는 것을 막고, 손 수정이 id 채번·상태
전이 규칙·문서 경로 불변식을 깨는 것을 막기 위해서다.

작업 **내용**을 알고 싶으면 `docs/tasks/<id>.md`를 직접 읽으면 된다. 이쪽은
막혀 있지 않다.

## 조회

```bash
node tools/backlog.mjs                      # 미완료 전체 (단계별)
node tools/backlog.mjs next                 # 선행이 끝나 지금 시작 가능한 것
node tools/backlog.mjs get 44               # 상세 + 선행·후행 작업
node tools/backlog.mjs list --phase 송장 --status todo
node tools/backlog.mjs list --category report --json
node tools/backlog.mjs stats                # 단계별 진행률
node tools/backlog.mjs check                # 무결성 검증 (오류 시 종료 코드 1)
node tools/backlog.mjs --help
```

id는 `44`, `t-044`, `T-044`, 제목 일부 모두 받는다. 단계도 `송장`처럼 일부만
써도 된다.

## 변경

```bash
node tools/backlog.mjs set 44 진행
node tools/backlog.mjs set 44 done
node tools/backlog.mjs set 19 대기 --note "T-001 공장 정보 확정 대기"
node tools/backlog.mjs edit 44 --priority P0 --deps "9,43" --where "lib/invoices/"
node tools/backlog.mjs add --title "인쇄 여백 보정" --category ui --phase "2. 송장" --deps 45
```

상태는 enum 값·한글 라벨·2글자 약칭을 모두 받는다.
(`in_progress` = `작업중` = `진행`)

## 작업 착수 = `in_progress` (예외 없음)

작업을 하기로 정한 순간, **손대기 전에** 상태를 바꾼다.

```bash
node tools/backlog.mjs set 44 진행
```

파일을 열기 전, 코드를 한 줄 쓰기 전, 서브에이전트에 위임하기 전이다.
작업이 끝난 뒤 몰아서 `todo → done`으로 건너뛰지 않는다.

**왜 꼭 해야 하나**

- 상태를 안 바꾸면 그 작업은 백로그상 **아무도 안 하고 있는 것**이 된다.
  다른 세션이 `next`로 같은 작업을 집어 중복으로 만든다.
- `next`는 `todo`만 보여준다. 진행 중인 것을 `todo`로 두면 계속 "시작 가능"
  목록에 남아 무엇이 실제로 남았는지 알 수 없게 된다.
- 턴이 중간에 끊기거나 컨텍스트가 정리됐을 때, `in_progress`가 **어디까지
  손댔는지 알려주는 유일한 표시**다. `node tools/backlog.mjs next`가 맨 위에
  "지금 작업중"으로 띄워 준다.

**흔한 변명과 답**

| 변명 | 답 |
| --- | --- |
| 금방 끝나는 작업이라 | 금방 끝나면 상태 바꾸는 비용도 작다 |
| 이미 반쯤 했는데 | 지금 바꾼다. 늦은 것이 안 한 것보다 낫다 |
| 어차피 곧 done으로 바꿀 건데 | done 커밋에 "진행 → 완료" 흐름이 남는 것이 기록이다 |
| 사용자가 직접 시킨 작업이라 | 백로그에 있는 작업이면 상태를 바꾼다 |

**작업을 끝내지 못하고 물러날 때**

- 이어서 할 거면 `in_progress`로 **둔다.** 그게 정상이다.
- 접기로 했으면 `todo`로 되돌리거나, 막힌 이유를 담아 `blocked`·
  `needs_decision`으로 옮긴다. `in_progress`로 방치하지 않는다.

백로그에 없는 즉흥 작업이면 `add`로 먼저 등록하고 `in_progress`로 바꾼다.

**이 규칙은 hook이 강제한다.** `in_progress`인 작업이 하나도 없으면
`task-claimed-guard.sh`가 산출물 파일의 Write·Edit를 차단한다.

면제되는 것 — 백로그 작업의 산출물이 아니라 그 작업을 준비·기록하는 파일들이다.

| 경로 | 왜 면제 |
| --- | --- |
| `.claude/**` | 하네스(규칙·hook·에이전트) 자체를 손보는 일 |
| `docs/**` | 문서와 태스크 브리핑 (`task-briefer`가 쓰는 곳) |
| 저장소 루트의 `*.md` | `CLAUDE.md` · `README.md` · `설계.md` |

Bash 경유 수정(`sed -i`, `>` 리다이렉트)은 막지 않는다. 문자열로 판별하면
오탐이 잦아서다 — 그쪽은 이 규칙이 맡는다. **우회 경로를 찾지 않는다.**

## 상태를 언제 쓰나

| 상태 | 약칭 | 언제 |
| --- | --- | --- |
| `todo` | 할일 | 아직 안 시작 |
| `in_progress` | 진행 | 지금 하는 중 — **착수 즉시 바꾼다** (위 절 참고) |
| `review` | 리뷰 | 만들었고 확인·검증이 남음 |
| `needs_decision` | 판단 | **사용자만** 할 수 있는 일 때문에 못 감 |
| `blocked` | 대기 | 선행 작업이나 외부 요인 대기 |
| `done` | 완료 | 완료 기준을 **실제로 확인**함 |
| `cancelled` | 취소 | 안 만들기로 함 (삭제 대신) |

- `blocked`·`needs_decision`·`cancelled`는 **`--note` 필수**다. 사유 없는
  대기 항목은 나중에 아무도 풀 수 없다.
- `needs_decision`과 `blocked`를 구분한다. 사장님이 엑셀 양식을 줘야 하면
  `needs_decision`, T-003이 안 끝나서 못 하면 `blocked`다.
- **막혔다고 멈추지 않는다.** 상태로 남기고 `next`로 다음 작업을 이어서 한다.
  턴을 마칠 때 `needs_decision` 목록과 사용자가 해줄 일을 함께 보고한다.
- `done`은 `docs/tasks/<id>.md`의 **완료 기준을 실제로 확인한 뒤**에만 쓴다.
  "만든 것 같다"로 done을 찍지 않는다.
- 작업을 시작할 때 `task-briefer`, `done`으로 넘기기 직전에
  `adversarial-reviewer`를 부른다 → `.claude/rules/서브에이전트.md`

## 커밋은 신경 쓰지 않아도 된다

- 백로그가 바뀌면 hook이 **자동 커밋**한다.
- 어떤 작업이 `done`이 되면 hook이 **작업 트리 전체를 커밋하고 push**한다.
  그래서 `done`으로 바꾸기 전에 작업 트리에 관련 없는 파일이 남아 있지 않은지
  본다.

## 무결성

`check`가 보는 것: 중복 id, enum 위반, 미존재·순환 선행 작업, 상태별 필수
필드(`done_at`, `note`), `doc` 경로가 id에서 유도되는지, 문서 존재 여부,
백로그에 없는 고아 문서.

CLI는 **저장 직전에 전량 검증**하고 실패하면 파일을 건드리지 않는다. 그래서
잘못된 명령으로 백로그가 깨지는 일은 없다.
